Claude Code 团队如何做代码审查

当 Agent 生成代码的速度越来越快，团队如何审查？Claude Code 团队没有取消审查，而是把更多阅读交给机器，把人的注意力留给真正需要判断的地方，并让错误更快暴露、更容易撤回。

Addy Osmani、Morgan Westlee Lunt、Qing Wang · 2026 年 10 月 15 日 · 原文约 14 分钟

文中数据：6 月到 9 月，Claude Code 仓库合并的 PR 数量翻了一倍多，需要回滚的比例下降了 40% 以上。作者将这归因于覆盖更广的自动审查、风险分级，以及快速回滚机制的共同作用。

重新思考代码审查的目的

Agent 写代码后，改动数量增长得很快。Anthropic 的单体仓库每天落地的改动，从当年 5 月约 2,500 个增加到 9 月超过 30,000 个。面对这样的速度，逐行人工审查很难持续。

代码审查有两个作用：在发布前发现并修复问题；帮助团队建立对代码库的共同理解。本文主要讨论第一个作用。

“有没有人读过代码”并不是一个准确的质量指标。更好的问题是：这项改动可能出什么问题？哪种检查——自动化还是人工——最适合发现它？

审查因此从 PR 末尾的一道关卡，变成贯穿开发过程的持续检查，像写作时的拼写检查。多数改动在交给人看之前，已经由 Claude 检查和修复过。

稀缺资源：人的时间和注意力

减少审查时间本身不够。如果坏代码引发故障，节省下来的时间又花在修复上，就只是把成本挪了位置。团队的目标是：大多数 PR 最多只需要一位人类参与者（可以是作者本人），同时不增加回滚和事故。

团队会观察每个 PR 的人工批准次数（中位数和第 95 百分位）、人工评论数量，以及 PR 等待人工处理的时间。回滚率和事故率是质量护栏：它们上升，就代表所谓的“省时间”并没有真正省下来。

一次改动的旅程

改动可能来自工程师的电脑，也可能来自 Slack 中的 Claude 会话。它会经过多层检查，再逐步到达用户。

一层一层检查，而不是只设一道关卡

每一层都会漏掉一部分问题，但漏网问题还会进入后续检查。只有穿过所有层的少数问题，才需要依赖发布后的监控和回滚。

1. 在别人看之前，先验证工作

给 Claude 能够运行的检查，例如测试、构建或与设计稿对照的截图，并要求它展示结果。随后让拥有新上下文的子 Agent 检查差异。提交 PR 前，团队成员还会用工具找缺陷、简化 diff、端到端检查行为；界面改动还要对照设计规范。

反复出现的审查问题应修在源头：技能、lint 规则或项目说明文件。CLAUDE.md 说明项目技术栈、约定、目标与非目标；REVIEW.md 说明代码所有者所在区域的风险、失败特征、忽略路径，以及报告问题时应提供的文件和行号证据。好的规则短而具体。

2. 每个 PR 都经过 AI 审查

Claude 将代码差异与整个仓库和 PR 意图对照，判断改动是否解决问题、是否符合系统设计、是否破坏其他功能；修复缺陷时会追查根因。多个 Agent 同时寻找缺陷，再由另一组 Agent 对发现投票。仅剩下足够可信的发现会成为行内评论，并按严重程度标注为“重要”“小问题”或“原有问题”。每一项都要修复，或说明为何不采纳。

团队上线研究预览时，获得实质性评论的内部 PR 比例从 16% 升至 54%。超过 1,000 行的 PR 大多会有发现，小型 PR 多数干净。每个仓库可选 Quick、Standard、Deep；漏掉缺陷代价越大，Deep 越值得。

3. 安全审查可以阻止合并

安全审查独立运行。缺陷审查或安全审查只要还有未解决发现，PR 就不能合并。作者修复问题，或简短说明这是误报。后续提交真正修复问题时，发现会自动清除。

4. 阻断式自动检查

常规检查包括 lint、类型检查、所有平台的测试和构建。一个 CLI PR 在人看之前，可能要通过数十项检查。PR 模板还会询问如何测试、如何撤回；Claude 可以填写，但提出改动的人负责确认。

5. 按风险分配人工批准

文档修复与自动更新器改动的风险不同，审查要求也不同。

风险示例需要的人工批准
低文档、文案、仅内部使用的功能、带功能开关的增量改动自动审查与安全检查通过后，可不需要
中普通产品改动；缓存、自动更新器、系统提示词等敏感部分1 人
高最高风险代码，以及指定为始终需要两人审查的路径2 人

风险由改动决定，而不是作者决定。分类器读取改动并分级，另一个分类器再判断是否仍需额外的人审。敏感路径和 CI 工作流文件始终要求人参与。轻量路径只对可信作者开放。Agent 的批准不能代替人的批准；指挥 Agent 改代码的人，和亲手写代码一样要承担责任。批准只对具体提交有效；出现系统无法确认的新提交后，必须重新批准。

6. 合并队列、功能开关与渐进发布

合并队列把 PR 放到最新主分支上重新运行检查，避免两个单独通过的改动组合后破坏主分支。新行为通常先通过功能开关开放给 Anthropic 内部员工。公开版本先进入 latest，之后才进入 stable。

7. 快速发现，快速回滚

仍会有错误漏过检查，因此最后一层是快速发现。功能开关可以不重新部署就关闭。Claude Code 有每周 on-call 轮值；事故复盘会追问哪一层本该发现问题。团队目前仍依靠作者、on-call 以及回滚和事故仪表板发现坏合并，希望在更多代码走向零人工合并之前增加自动熔断机制。

放慢速度确实可能减少错误，但很大程度上只是因为做得更少。团队更愿意提升发现和修复问题的速度。

如何让审查器变得更好

审查流程通过持续评估来改进。任何事故都可以变成评估案例：团队收集造成事故的 PR、后续修复和回滚，请熟悉代码的工程师确认缺陷及其所在位置，再每天用这些案例运行审查器。

团队还通过作者如何处理评论来衡量噪声：修复了、认为错误、说明行为是有意的，或认为不值得处理。也会在已知干净的 PR 上运行审查器，统计它是否提出了可能引发有害修改的建议。明确的优先级是：先抓住真正的缺陷，再减少审查轮数。

噪声对 Agent 作者的成本更高：人可以很快略过一个小意见，Agent 可能真的去改代码，带来新提交和新一轮审查。审查必须收敛。某个 CLI PR 曾一夜之间经历 50 多轮审查与修复。调查发现，审查器反复指出的代码中，约 59% 从第一次审查时就已存在；它经常是在后续轮次补报旧问题，而非发现新问题。

团队之后增加了轮数上限：三轮之后要求作者重新思考方案；前几轮后只复查新增 diff；指出问题类别，让作者一次修完所有同类问题；不重复已经发布的发现。审查 Agent 也会夜间扫描既有代码，提前发现旧缺陷。

人继续留在环路中的地方

让资深工程师从深度工作中抽身，只为发现常规小错误，成本很高。团队仍把以下工作交给人：

  • 判断是否值得做：方向、品味和范围。要问“我们真的应该做这件事吗？”
  • 审查高风险代码：例如账单、自动更新器和 CI 工作流。
  • 审查会被他人仿效的架构决策。
  • 阅读证据：测试输出、实际运行的命令及其结果、截图和审查发现。如果说不清检查会漏掉什么，就要认真请人审查，而非快速点过。
  • 对最终结果负责：不论代码由谁输入，发布的人类都要承担责任。

团队如何共享对代码的理解

代码审查也承担知识共享的作用：阅读队友的 diff，能了解改了什么、模块如何连接。但团队并不要求有人把整个 Claude Code 的结构都记在脑中。需要理解某个局部时，就让 Claude 针对那一部分写说明，几分钟便能生成，而且符合代码的当前状态。

有些人会进一步让 Claude 制作小型可视化材料，按自己喜欢的方式讲解模块。团队开放频道的工作习惯也让成员能看到彼此正在构建什么，在过程中互相补充。

“你合并，你负责”

如果你合并了一项小型或中型改动，后来出问题，通常由你来修复。这套方式建立在几个条件上：

  • 改动足够小，容易审查、调试和回滚；
  • 一切都可撤回，功能开关、回滚和分阶段发布能在几分钟内撤销大多数错误；
  • 影响范围决定门槛，代价高的代码需要更多人和更多检查；
  • 遥测与内部使用能快速暴露回归；
  • 负责修复不是追责甩锅。作者上下文最多，事故复盘看的是系统。

责任也是共享的。开放频道让任何人都能看到其他人在做什么、接续讨论，或让 Claude 检查遗漏。来自代码所有者之外的反馈，也帮助团队在不逐行设卡的情况下保持质量。

该改变方向时就改变方向

Agent 让启动工作变得便宜，也意味着有些工作不该合并。有人可以在频道里指出先前决策、追问原因或提出更简单的做法，作者就关闭或调整 PR。关键是尽早在讨论中提出不同方向，不要等 PR 完成后才用阻塞评论提出。

如何采用这套流程

文章认为，大部分工具和机制现在已经可用。

提交 PR 之前

  • 在简短的 CLAUDE.md 中列出 Agent 可运行的检查；用 hooks 执行格式化和 lint。
  • 本地运行 /code-review、/security-review，或用新上下文的子 Agent 复审。
  • 新增 REVIEW.md，把反复出现的意见整理成规则。

每个 PR 都执行

  • 要求 CI 通过；PR 模板包含“测试”“风险”“如何回滚”。
  • 先在一个仓库启用 AI 审查，调好 REVIEW.md 后再推广。
  • 添加自动安全审查，要求合并前处理完所有审查讨论。
  • 按风险选择快速或深入审查；漏掉缺陷代价高时，选择 Deep。
  • 限制审查轮数；前几轮之后只复查新 diff。

批准、合并与发布

  • 写下风险等级，让等级由改动决定；先严格，再依据证据逐步放宽。
  • 只给可信作者开放轻量批准流程。
  • 用 CODEOWNERS 和分支保护规则，让认证、账单、CI、发布工作流和安装器始终有人审查。
  • 机器人批准不能代替必需的人审；有新提交时撤销旧批准。
  • 使用合并队列、功能开关、内部先用、分阶段发布和一步回滚。
  • 把事故与回滚加入评估集；提示词、工具或模型变化时重新评估审查器。
  • 度量人工耗时，同时用回滚率和事故率守住质量。

文章的方向

批准 PR 仍然是人的决定。Claude Code 的公开审查产品提供问题发现，不代替人批准；Anthropic 自己的仓库则进一步允许部分低风险改动仅凭自动检查合并。

审查漏掉问题时，团队会问模型当时缺少什么信息，再把修正写进 CLAUDE.md、技能或新的检查中。目标没变：降低每项改动消耗的人工时间，同时不增加回滚和事故。

核心不是把所有代码都交给机器，而是让机器承担可重复的检查，让人把时间花在方向、风险和证据上，并让每项改动都容易验证、监控和撤回。
