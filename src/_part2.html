3 二十三本 playbook

playbook 不能直接调用，只能由 poteto-mode 按任务选中。你要学的是「什么任务对应哪本」，以及「这本会保证什么」。

下面按使用频率分组。每本给四样东西：什么时候选它、它保证什么、产物是什么、什么时候别用。

诊断类

Investigation 调查

只读最常见用于「这是怎么跑的」「当初为什么这么写」「我们确定吗」。不写代码，只产出带引用来源的答案。产物是一份说明，每个结论都指向具体文件和行。别用在你要它顺手改掉的地方。

Bug fix 修缺陷

高频有明确症状的缺陷。它保证三件事：在真实界面上复现、每一步有运行时证据、修复前先放能复现问题的测试。产物是修复加证据，通常还有一个 PR。别用在你只有一个模糊感觉的时候，那属于 Investigation。

原文六步，以及你会看到什么。

  1. 自己复现。在出问题的同一个界面上驱动一遍，不让你去复现。复现不了就合成触发条件、收紧条件、加埋点，直到它稳定出现。你会看到一条真实命令和它的输出。
  2. 二分排因。先列候选假设，再逐个排除。用 how 看这块子系统怎么跑，用 why 查回归历史。每轮挑最能缩小问题空间的那一刀。状态看不清就加日志，不猜。确认的是机制，不是症状。
  3. 规划修复。跨函数边界先 architect，然后按具体范围派实现子代理。范围要写清文件、数据形状、成功标准。
  4. 回同一界面验证。原来失败的操作现在通过才算过。「不确定」或者换了界面验证都不算。单测只能证明分支行为，不能证明缺陷消失。
  5. 排列提交顺序。失败的复现先落进历史，修复在后。有廉价测试就走测试先行，没有就跳过，不要为了形式造测试。
  6. 开 PR。描述里写清什么坏了、根因、修复、怎么验的，引用决定性的输出。
一条硬规矩。每一行改动都要能追溯到运行时证据。「可能有帮助」的保险代码属于假设，不上线。证据推翻了假设，就把当初因它而加的改动回滚掉。

Perf issue 性能问题

有可测的慢。核心是把每个修复绑定到一个测量，先建基线再改。产物是前后数字。别用在「感觉有点卡」这种没有指标的场景，先做 Investigation 或 Runtime forensics。

Hillclimb 爬坡

一个指标要长期、科学地提升，不是一次修好。每轮一个假设，前后测量，接受就提交一个 commit，写决策日志。产物是一串可回滚的小胜。别用在一次性修复上，那是 Perf issue。

Runtime forensics 运行时取证

进程还活着，症状是泄漏、空转、偶发卡死。做活体观测，不靠读代码猜。产物是诊断，不是修复。

Trace forensics 轨迹取证

别人给了你一份已经抓下来的 profile、trace、spindump 或堆快照。产物同样是诊断。

开发类

Feature 新功能

高频新行为或行为变化。第一个动作是命名数据结构，再定实现形状，然后设计、实施、验证。产物是功能加验收证据。别用在纯结构调整，那是 Refactoring。

原文八步。

  1. 先懂再改。用 how 把受影响的子系统读一遍。
  2. 并行设计。architect 让多个模型各出一版类型与签名，交叉评审后合成。
  3. 写吞吐检查点。四条待办：哪些步骤必须先做、哪些工作流互不依赖可并行、哪些共享可变状态要先拆、最小安全拆分是什么。不适用也要保留条目写 n/a: 原因，不能删。
  4. 派实现。给子代理文件路径、命名的数据形状与组织方式（状态机而不是散落布尔、表驱动而不是分支堆叠、类型化模型而不是重复形状假设）、成功标准。实现有多种合理形状时改用 arena。每个写文件的代理给独立工作树，不许在一份共享文件上并行。
  5. 在匹配的界面验证。换了界面或者结论不确定都不算通过。
  6. 重排提交。拆成小的、有顺序的提交，每段自证后再下一段。
  7. 争议设计先对抗。设计有争议就 interrogate，再交付。
  8. 开 PR。说清做了什么、为什么这样选、吞吐检查点、未决问题。
怎么读一份 SKILL.md。四段顺序读：先看 frontmatter 的 description，它决定这个技能会不会被触发；再看开头的非协商项，那是约束；中间是步骤；最后看回报格式，那是你验收它的模板。正文不用背，知道去哪找就行。

Refactoring 重构

行为不变，只改形状。它保证每一步都有等价的检查点。别用在你会顺手加功能的时候，那会同时改行为和形状，出了问题分不清是哪边。

Prototype 原型

一个决定凭推理定不了，做个一次性的东西让结果说话。可以是布局、交互、也可以是「这个方案到底跑不跑得动」。产物是决定，代码扔掉。别用在你已经知道要什么、只缺实现的时候。

Visual parity 像素对齐

两套实现要看起来完全一样，或者迁移样式系统。基线是规格，不能动。产物是图像 diff 证据。

Authoring a skill 写技能

写或改一份 SKILL.md。它管的是技能的语气、触发描述、结构和自证方式。

Eval 盲测

验证一次技能或提示词的改动，是否真的改变了 agent 行为。做法是给候选者不含任何评测词汇的自然任务，用不同模型各跑一遍，再由一个不知道来源的评委按评分表打分。别用在你只想跑一次看看效果，那是直接执行。

交付类

Babysit 看 PR

高频PR 开着，要把它推到可合并。处理冲突、跑 CI、挑评审意见。产物是可合并状态，不合并。合并权永远在人。

Shipping 上线

一串 PR 已经绿了。绿不等于安全。每个 PR 先由一个没写过这段代码的代理独立验证，只有从根部连续通过的那一段才落地。

Opening a PR 开 PR

每本 playbook 的收尾步骤。它管 PR 描述的结构、自测说明、风险与回滚。

自主类

Autonomous run 自主运行

「一直跑到 X 为止」。你必须先给出一个能判定的完成条件，它才有停止的依据。没有判定条件时别用，会变成无限循环。

Orchestrate 编排

多天、多 PR、几十个子代理的项目，交给一个协调会话。它和 Autonomous run 的区别是规模与形态，不是自主程度。

Autopilot-full 全自动队列

一批互不依赖的 PR，全部推到可合并。每个 PR 一个负责人，根部再统一验证。操作者负责点合并。

Autopilot-stack 堆叠队列

和上面一样，但 PR 之间有依赖，最后交给人一次性落地。

衔接与清理类

Session pickup 接手

接别人的分支、别人的会话。先读已有记录，不重做。

Pause safely 安全暂停

要断线、要重启、上下文快满了。产出一个冷启动能接上的检查点。

Multi-phase plan 多阶段计划

跨阶段或跨 PR 的工作，先出计划，不实施。

Worktree and simulator cleanup 清理

清磁盘。审计后只删已合并或已放弃的工作树和过期模拟器。

选错的成本。选错 playbook 比做错一步贵。修 bug 用了 Feature 流程，会多出一堆设计与验收；做功能用了 Bug fix 流程，会缺设计、缺数据形状，返工更贵。判断不准时先问一句「这是新行为还是旧行为坏了」。

43 个可调用技能。读法：先记住分组，再记每组里你最常用的三四个。全部背下来没有意义，知道去哪个组找就够了。

5 二十四条原则

原则是单规则技能，平时不用叫。它们的作用是当 poteto-mode 面临取舍时提供偏向。你记住名字，就能用一句话纠正它，例如「按 prove it works，把真实输出贴出来」。

原则一句话什么时候用它纠偏
prove-it-works验真实产物，不验代理指标它说「编译通过」「测试绿了」就宣告完成
fix-root-causes顺症状追到第一次出错的地方它在加防御性代码而不是找根因
test-behavior-not-implementation断言用户能观察到的行为测试改了实现就碎
sequence-verifiable-units切成每段都有检查点的小单元一次改动太大、无法中途验证
laziness-protocol能删就删，最小改动它在加抽象、加层、加信号线程
foundational-thinking先把核心类型和数据结构定对开工就写逻辑，没定数据形状
redesign-from-first-principles新需求进来时，按「一开始就该这样」重设计在旧结构上打补丁
attack-the-premise两个修法失败且共享同一前提，就别再修，去验前提第二次修复又没解决
subtract-before-you-add先删死代码和冗余，再加在新旧并存的状态上继续叠
minimize-reader-load减少层数与隐藏状态代码难追、需要来回跳
outcome-oriented-execution直奔目标架构，不保留过渡态为兼容保留了没人要的中间态
experience-first用户感受优先于实现便利在拿「实现麻烦」当理由砍体验
exhaust-the-design-space没有先例时，做两三个原型再定直接采纳第一个方案
build-the-lever造工具去做或去证明，别手工重复同一件事手工做了第三遍
model-the-domain用状态机、类型、表驱动代替散落条件分支越写越多、形状假设重复
boundary-discipline校验集中在系统边界，内部信任类型每个函数都在重复校验
type-system-discipline让非法状态无法表达用布尔组合表示互斥状态
make-operations-idempotent崩溃重跑收敛到同一结果重试会重复写、重复发
migrate-callers-then-delete-legacy-apis迁移与删除同一波做完新旧 API 长期并存
separate-before-serializing-shared-state先消除共享，再谈串行化多个执行者写同一文件或对象
guard-the-context-window大输出走子代理，主线只留结论主线在堆原始日志
never-block-on-the-human可逆的事直接做，做完给人看它在问「要不要我做」
encode-lessons-in-structure同一条指令写第二遍时，改成 lint 或脚本你在反复提醒同一件事
explain-the-number报数字前先弄清它在量什么、被什么限制任何性能或评测结论
怎么用原则。不要一次背二十四条。记住三条就够撑起大部分判断：prove-it-works、fix-root-causes、laziness-protocol。其余在遇到具体场景时回这张表查。
