0 怎么用这本手册

这本手册只有一个目的：让你把 pstack 的体系学明白，学完能自己判断一件事该走哪条流程、会用哪些技能、能预判它会怎么做。

它不是命令大全。命令在附录 A，随查随用。正文讲的是「为什么这样设计」和「什么情况下选哪个」。

怎么读

  • 第一次读：从第 1 章顺序读到第 6 章。大约 90 分钟，不需要电脑，只需要这本手册。
  • 每读完一章，翻到第 13 章做对应那张复述卡。讲不出来就回读，不要往下翻。
  • 第二次读：只读第 3、4 章的表格，把每个技能名字和一句话用途对上号。目标是看到任务能立刻说出该叫谁。
  • 动手前读：第 7 章验证、第 8 章并行。这两章决定你最终能跑多大。
  • 想知道「这套东西边界在哪」：直接读第 15 章，不必先读前面。
  • 有整块时间：读第 1 到 6 章加第 10 章纸笔练习。练习只要求纸笔或一个空编辑器。

学完的验收标准

手册开头说的「原作者的七八成」，拆成下面五条可检验的能力。全部做到算达到，做不到的条目回对应章节补。

0.5 十分钟，一个故事

先不看任何名词。讲一件事怎么从进来到做完。

事情

你发现一个毛病：快速连按快捷键切换侧栏，中间几次像是没反应。你想让它修好。

你会怎么做

如果你自己动手，大概是这几步。

  1. 先让它重现出来。点几下，确认真的会吞。
  2. 猜几个原因。是按键没收到，还是收到了被忽略，还是界面没来得及画。
  3. 一个个排除。加一行日志，看按键到底有没有进来。
  4. 找到原因，改那一处。
  5. 回到同一个地方再点一遍，确认不吞了。
  6. 把这次改动交上去，顺手写清楚是怎么回事。

这套东西做的，就是把这个顺序固定下来，并且要求每一步都留下能复查的痕迹。它不比你聪明，它只是不会偷懒跳过第二步和第五步。

名词是怎么长出来的

上面那六步，被写成一份清单。清单不止一份，修毛病有一份，做新功能有一份，看别人提交的改动也有一份。这些清单叫 playbook。

谁负责看你的话，判断该翻哪一份清单？一个专门的角色，叫 poteto-mode。

清单里某一步需要一个专门动作，比如「先把这块代码读懂再动手」。这个动作也有一份说明，叫技能。它和清单的区别是：清单一整本，技能一个小动作。

做的过程中容易走偏的地方，用一句话提醒自己，比如「没验证过的不算完成」。这些话叫原则。

最后，「回到同一个地方再点一遍」这一步，被单独做大了。因为作者认为，前面都做得对，只要这一步偷懒，结果就是不可信的。这套东西叫验证技能。

一张对照表

故事里的说法正式名字它解决什么
一整套做事顺序playbook防止漏步、防止顺序颠倒
看活派单的人poteto-mode判断这是哪类活
清单里的一个专门动作技能把一件事做到位

为什么这套东西值钱

因为它把「靠自觉」换成了「靠流程」。自觉靠不住，尤其是让机器干活的时候。流程可以检查，自觉不能。

剩下的十二章，都是在这六步上做加法。读完故事，你已经知道它在干什么了。

1 全景：四层结构

一句话：pstack 不是程序，是六十七份写给 AI 看的说明书，加一个负责分派的总管。

它的组织形式和一般「提示词库」不同。提示词库是平铺的，越用越乱。它是四层，每层职责单一。

四层

层是什么数量能不能直接叫
路由器poteto-mode。判断任务类型，挑一本 playbook，把步骤抄进待办，然后按步骤调用技能和子代理1能，/pstack:poteto-mode
playbook一类任务的步骤清单。修 bug 六步，做功能五步，看 PR 三步23不能。只能由 poteto-mode 读
技能一个具体动作或一种专门视角。理解代码、审 diff、写文档、生成验证器43能，/pstack:<名字>
原则一条约束。写代码、测试、排查、重构时用来纠偏24能叫但很少叫，通常由 poteto-mode 引用

为什么这样分。因为三种东西的生命周期不同。playbook 会随流程演进改，技能会随工具改，原则几乎不变。混在一起写，改一处就伤全局。

为什么 playbook 不能直接叫

这一点最容易误解，也最能说明设计意图。playbook 是「步骤清单」，不是「动作」。清单单独执行没有意义，它需要有人先判断任务类型，再把清单里的每步翻译成具体的技能调用和子代理派发。

所以正确的用法是描述任务，不是描述步骤。你自己列步骤，反而会把 playbook 里更合理的顺序打乱。

别这样写：

/pstack:poteto-mode 先读代码，再写测试，再改，再跑测试

这样写：

/pstack:poteto-mode 修好快速连按 ⌘B 会吞键的问题。完成标准是在真实 App 里 6 次连按全部生效，并且给我前后截图。

三种最常用的开口方式，直接复制改括号里的内容。

# 1 修缺陷
/pstack:poteto-mode 修好 <可复现的症状>。用 verify 技能复现，修好后给我前后证据。

# 2 做功能
/pstack:poteto-mode 给 <某个页面或模块> 加 <功能>。先定数据形状，再实现，完成后用 verify 技能验证并给我截图。

# 3 只问不改
/pstack:how <某段代码或某个流程> 是怎么工作的？给我文件路径和关键函数。

它和 CLAUDE.md 的区别

CLAUDE.md 是常驻上下文，每次会话都全文加载。pstack 的技能是按需加载，只有 description 常驻，正文在命中时才读。这让它可以放很多技能而不撑爆上下文，代价是路由必须准确，描述写不好就等于这个技能不存在。

核心赌注

整套东西押在一个判断上：如果 AI 能自己验证工作，人的角色就从「盯着每一步」变成「定义什么算完成」。验证能力是地基，其余是上层建筑。

这也是为什么验证技能被作者称为关键基础设施，而别的技能只是工具。

2 技能如何运行

这一章讲机制。理解机制，你才能预测它的行为，而不是背规则。

一个技能就是一个目录

skills/
  how/
    SKILL.md        <- 唯一必需的文件
  create-verification-skill/
    SKILL.md
    references/     <- 可选，正文按需引用

SKILL.md 开头是 YAML frontmatter，其中 description 是全文最关键的一行。会话启动时，所有技能的 description 被注入上下文，模型按语义匹配。匹配不上，正文永远不会被读。

---
name: blast-radius
description: Find what a change could break somewhere else before it ships...
---

所以「学会一个技能」等于「知道它的 description 覆盖哪些说法」。这也解释了为什么同一个技能，你说「影响面」它能触发，说「看看会不会坏」也可能触发，说「评估风险」就不一定。

启动钩子

插件装了一个 SessionStart hook，在启动、恢复、清空、压缩上下文时注入 poteto-mode 的强制段。其中一条是：改动涉及两个以上文件时，建议进入 poteto-mode。

这就是为什么你只是随口让它改点东西，它却开始走流程。不想要这个行为，在模型表里写 session hook: off，重启会话生效。

模型表

技能本身不绑定模型。哪个角色用哪个模型，由运行时读一份覆盖表决定，路径是 ~/.claude/pstack-models.md。表里每行是「角色: 模型」，可以带推理强度后缀，例如 opus @xhigh。

面板类角色（arena、architect、interrogate）的值是列表，列表里每一项都会起一个子代理，所以列表长度直接决定花费。

关键区别。模型表只影响「谁来干」，不影响「干什么」。改模型表不会改变流程，只会改变成本和一次跑几个。

子代理

重活都派给子代理。主线程只保留判断和汇总，不保留大段原始输出。这不是风格问题，是上下文预算问题。一次读十个文件、跑十次验证，主线程自己干，上下文很快被塞满，后面的判断质量会下降。

子代理分两种用法：新任务开新的，只有确实需要它本地状态时才续用旧的。续用旧代理时，中途追加的指令有丢失风险，重要变更要重新完整交代。

一次任务进来，发生了什么

  1. 你的消息进入主线程，同时技能清单和钩子指令已在上下文里。
  2. 主线程判断这是哪类任务，命中某本 playbook，把步骤抄进待办清单。
  3. 按步骤调用技能，或派子代理执行。
  4. 需要验证时调用验证技能，失败就回到对应步骤。
  5. 收尾时按 playbook 自己的回报格式输出，并说明哪些步骤被跳过、为什么。

第 2 步的产物是待办清单，你能直接看到它选了什么、准备怎么做。这是最值得盯的地方。选错 playbook，后面全歪。

一个可操作的习惯。每次 poteto-mode 启动后，先看它抄进清单的前三条是不是你预期的步骤。不对就立刻停，说「这是新任务，应该按 X 处理」。改流程比改结果便宜。
