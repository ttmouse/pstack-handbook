# Boundary Discipline

把校验、类型收窄和错误处理放在系统边界。无条件信任内部代码。业务逻辑放在纯函数里。外壳要薄、要机械。

**为什么：** 散落各处的校验噪音大、重复，还给出虚假的安全感。把逻辑从框架接线里拿出来，才能脱离框架测试它。

**模式：**
- **在边界上**（CLI 参数、配置文件、外部 API、网络协议）：校验、返回错误、防御性处理。
- **系统内部：** 类型化数据、错误传播、不做重复校验。信任类型。
- **跨越边界。** 暴露领域概念，而不是边界的私有表示。把通用机制留在内部，把专用策略放在边缘。

**应用场景：**

校验与错误处理：
- 在解析时（边界处）校验配置，而不是在业务逻辑里校验
- 在边界把原始数据解析成领域类型
- 不要把传输层、存储层、框架或线上格式类型从公共接口再导出
- 如果边界已经校验过，调用链深处不要做冗余的 nil 检查

代码组织：
- 业务逻辑放在没有框架依赖的纯函数里
- 解析函数：从原始字节到类型化状态的纯转换
- Prompt 构建：结构化状态进，字符串出
- 评分与评估：从状态到结果的纯转换

**检验标准：**
- 「这份数据现在正在跨越系统边界吗？」如果不是，校验就是冗余的。
- 「它能不能成为外壳直接调用的一个纯函数？」如果能，就抽出来。
