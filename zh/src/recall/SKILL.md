# Recall

在 GitHub Copilot 上，先读[平台映射](../poteto-mode/references/copilot-tools.md)（包括其中的逐技能说明），再执行本技能。

在 Muse 上，先读[平台映射](../poteto-mode/references/muse-tools.md)（包括其中的逐技能说明），再执行本技能。

在 Antigravity 上，先读[平台映射](../poteto-mode/references/agy-tools.md)（包括其中的逐技能说明），再执行本技能。

**在开始或恢复工作之前，你重建用户最近的工作上下文，并交回一份紧凑的胶囊：现在到哪了、下一步做什么。**

保持紧凑、贴题。只读范围内线程需要的东西，然后停。

你的上下文活在两份记录里。你自己的聊天历史存着你做了什么、决定了什么。共享记录存着同一批代码在别的名下发生的一切：用户反复报的症状、发布了又被回退的修复、还在生产上触发的错误。第二份记录就是 **why** 技能搜索的对象，覆盖源码控制、issue 跟踪器、聊天与 issue 频道、长文档、错误追踪。一个带着长 bug 尾巴的功能，故事大多在那里，所以不要只凭你自己的转录重建它。

转录位于 `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/<encoded-cwd>/<uuid>.jsonl`。每行一条聊天消息。跑 `node <plugin>/skills/reflect/scripts/claude-project-dir.mjs` 打印本次会话的目录，不要手工拼 `<encoded-cwd>`。Claude Code 把 ASCII 字母和数字以外的每个字符换成「-」（所以 `/Users/you/my_app.web` 变成 `-Users-you-my-app-web`），超过 200 字符的名字用哈希缩短，设置了 `CLAUDE_CONFIG_DIR` 时以 `CLAUDE_CODE_PROJECT_DIR_NAME` 顶替。

1. 先分类，再路由。要恢复的是一次具体的过往对话，那是 `session-pickup` playbook，不是本技能。把习惯变成持久技能是 `automate-me`。要一份人类可读的工作总结是另一个任务。Recall 是在你行动之前加载跨近期聊天的工作上下文。用户已经给了完整的现状胶囊（路径、分支、改动），就用它，跳过挖掘。
2. 搜索前锁定范围。钉住时间窗（「最近」是真实区间，默认最近 7 天）、主题（如果点名了）、工作区（默认活跃的那个。没被要求绝不读别的项目的转录）。把范围复述回去。绝不悄悄把「全部」变成「最近 N 个」。
3. 在你的聊天历史上扇出。在快而便宜的模型上生成并行子代理，每个拿语料的一个切片。告诉每个子代理按真实修改时间（`ls -t`）排候选、绝不按 UUID 名排，先 grep 主题再只读命中的聊天、且只读它们的相关区域，跳过当前聊天和明显噪声（子代理、eval、测试聊天）。每个返回同一个 schema，每个聊天一块：主题、用户的目标、决策、未结线程、挣扎与纠正、产物（PR、工单、分支），每条引用聊天 UUID。只有一两个聊天时跳过扇出，直接搜。原始转录留在子代理里。主线程只拿它们的发现。按 **poteto-mode** 技能的 Subagents 小节，为工作选择每个子代理的推理强度。
4. 主题点名某个功能、文件、子系统、区域、或 bug 时，扫共享记录。这是默认，不是判断题，「my work on X」也不豁免。交给 **why** 技能的源码调查者，但把问题从「为什么建成这样」转向「现状是什么、试过什么没站住、用户还在报什么」。复用它的逐源 playbook，调查者与聊天历史挖掘并行跑，继承它的姿态：每个源一个调查者、空结果是发现、不可用的 MCP 跳过并说出来。把返回的东西并进简报。在报告任何东西「从未被记录」之前，还要扫一遍项目常备规则点名存放排队或已记录条目的每个位置（memory 目录、决策日志、`.planning/` 树、项目 CLAUDE.md 指针）。漏掉项目规则点名的某个地方的搜索不算穷尽。只有纯活动回忆、没有命名目标时（「我这周做了什么」）才跳过这一步，那时你自己的历史和活体状态就是全部答案。
5. 关于人类裁定的主张，应用[Claims about human decisions](../why/references/epistemics.md#claims-about-human-decisions)。范围精确性重要时保留可归属的原始措辞和来源，把代理的解释分开存放，把复制的摘要当作一条证据链。
6. 对照活体状态核实。拿挖掘和扫描浮出的 PR、分支、工单，用 `git` 和 `gh` 核查。答案取决于某个代理实际做了什么（跑了哪些工具、读了哪些文件、撞了哪些错误）时，读完整转录，不是裁剪过的本地副本。
7. 按下面的契约写简报。按线程分组。贴着点名的主题。

## 输出契约

先胶囊，然后线程状态，然后问题，然后下一步。更深的细节放底下或砍掉。

- **Capsule（胶囊）。** 最多 5 条 bullet。这份工作是什么、整体到哪了。
- **Threads（线程）。** 每条一行，前缀恰好一个状态标签：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]`、或 `[planned, not started]`。没有标签的线程就是还没做完，所以给它打标签。
- **Problems（问题）。** 最多 5 条，反复出现的那些。包含用户反复报的症状、任何发布了又被回退的修复，让下一次尝试从上一次失败的地方开始。
- **Next move（下一步）。** 单个最有用的下一步动作，具体。

相邻的功能或工单不进简报，除非它阻塞这一个。胶囊和线程行超出一个屏幕时，先砍细节后砍线程。简报通过 **unslop** 技能写，聊天发现按 UUID 引用，共享记录发现按其来源引用（PR #、工单 ID、聊天永久链接、错误追踪 issue），公开输出前先消毒私人上下文。

**回复：** 简报本身，按上面的契约。
