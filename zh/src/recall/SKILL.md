# Recall

在 Codex 上，先阅读[平台映射](../poteto-mode/references/codex-tools.md)（包括其中的各技能说明），再执行本技能。

在 GitHub Copilot 上，先阅读[平台映射](../poteto-mode/references/copilot-tools.md)（包括其中的各技能说明），再执行本技能。

在 Muse 上，先阅读[平台映射](../poteto-mode/references/muse-tools.md)（包括其中的各技能说明），再执行本技能。

在 Antigravity 上，先阅读[平台映射](../poteto-mode/references/agy-tools.md)（包括其中的各技能说明），再执行本技能。

**在开始或恢复工作之前，重建用户最近的工作上下文，交回一份紧凑的简报：现状如何、下一步做什么。**

保持紧凑且不离题。只读范围内线程需要的东西，读完就停。

你的上下文存在于两份记录里。你自己的聊天历史记录你做了什么、决定了什么。共享记录记录在别的名义下围绕同一代码发生的一切：用户反复报的症状、上线又被回滚的修复、仍在生产环境触发的错误。第二份记录在源码控制、issue 追踪、聊天与 issue 渠道、长文档和错误追踪里。一个 bug 尾巴很长的功能，它的大部分故事都在那里，不要只靠你自己的转写记录重建。

转写记录位于 `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/<encoded-cwd>/<uuid>.jsonl`。每行是一条聊天消息。运行 `node <plugin>/skills/reflect/scripts/claude-project-dir.mjs` 打印本次会话的目录，不要手工拼 `<encoded-cwd>`。Claude Code 把 ASCII 字母和数字以外的每个字符换成「-」（`/Users/you/my_app.web` 变成 `-Users-you-my-app-web`），超过 200 字符的名字用哈希缩短，设置了 `CLAUDE_CONFIG_DIR` 时改用 `CLAUDE_CODE_PROJECT_DIR_NAME`。

1. 先分类再路由。要恢复某一次具体的旧对话，那是 `session-pickup` playbook，不是本技能。把工作习惯变成持久技能是 `automate-me`。要一份人类可读的工作总结是另一回事。Recall 是在你行动之前，跨近期对话装载工作上下文。用户已经给了一份完整的状态胶囊（路径、分支、改动内容），就用它，跳过挖掘。
2. 搜索前先锁定范围。定下时间窗口（「最近」是一个真实范围，默认最近 7 天）、主题（如果点名了）和工作区（默认当前活跃的那个。绝不未经要求读别的项目的转写记录）。把范围复述给用户。绝不悄悄把「全部」变成「最近 N 条」。
3. 在聊天历史上扇出。用快而便宜的模型启动并行子代理，每个分一块语料。要求每个子代理按真实修改时间排序（`ls -t`），绝不按 UUID 名排序；先 grep 主题，只读命中的聊天，且只读其中相关区段；跳过当前聊天和明显的噪声（子代理、eval、测试聊天）。每个返回同一模式，每个聊天一块：主题、用户目标、决定、未决线程、困难和纠正、产物（PR、工单、分支），每项都引用聊天 UUID。只有一两个聊天时跳过扇出直接搜。原始转写留在子代理里，主线程只拿发现。按 **poteto-mode** 技能的 Subagents 章节，为每个子代理按任务选择推理力度。
4. 只要主题点名了某个功能、文件、子系统、区域或 bug，就扫共享记录。这是默认动作，不是自由裁量，「my work on X」不能豁免。每个来源启动一个调查子代理，给完整工具权限（受限的 agent 类型会砍掉 MCP 访问），问「现状如何、试过什么但没站住、用户还在报什么」。与聊天历史挖掘并行跑。空结果也是发现。不可用的 MCP 跳过并说明。在报告任何「从未被记录」之前，把项目常备规则点名的每个存放位置（记忆目录、决策日志、`.planning/` 目录、项目 CLAUDE.md 指针）都扫一遍。跳过了规则点名位置的一轮搜索不算穷尽。只有纯活动回顾且无点名目标时（「我这周干了什么」）才跳过这步——那时你自己的历史和实时状态就是全部答案。
5. 涉及人类裁决的说法，在精确范围要紧时找到当事人原话。保留来源指针、发言人，以及足以确定范围的原话量；代理的摘要或解释要明确标注。仅凭转述不能确定范围。原话拿不到就说拿不到，让范围保持不确定。同一种解读的多份副本是一条证据链，不是相互独立的决定。
6. 对实时状态核实。把挖掘和扫描浮出的 PR、分支、工单，用 `git` 和 `gh` 核一遍。答案取决于某个 agent 实际做了什么（跑了哪些工具、读了哪些文件、遇到了什么错误）时，读完整转写，而不是精简的本地副本。
7. 按下面的契约写简报。按线程分组，不离点名主题。

## 输出契约

先放胶囊，再放线程状态，然后是问题，最后是下一步。更深的细节往下放，或删掉。

- **胶囊。** 至多 5 条要点。这项工作是什么、整体进展到哪。
- **线程。** 每条一行，行首恰好一个状态标签：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。没标签的线程就是还没完，补上标签。
- **问题。** 至多 5 条，挑反复出现的。包括用户反复报的症状、上线又被回滚的修复，让下一次尝试从上一次失败的地方开始。
- **下一步。** 单个最有用的下一步动作，具体。

相邻的功能或工单不放进来，除非它阻塞当前这个。当胶囊和线程行超出一个屏幕，先砍细节，不砍线程。简报用 **unslop** 技能写；聊天发现按 UUID 引用，共享记录发现按其来源引用（PR #、工单 ID、聊天永久链接、错误追踪 issue）；任何公开输出之前先清洗私有上下文。

**回复：** 简报，按上面的契约。
