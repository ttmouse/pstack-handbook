# Separate Before Serializing Shared State

当并发参与者可能共享可变状态时，先问他们是否需要同一个可变对象。如果不需要，消除共享。当共享是真实的，就在结构上强制串行化：锁文件、顺序阶段、独占所有权。指令和约定不是并发控制。

**为什么：** 对共享状态的并发写入会产生间歇性、难复现、调试昂贵的竞态条件。

**模式：**
1. **识别共享的可变状态**（双方都读写的文件、双方都推送的分支、双方都定义和消费的 API）。
2. **默认做法：消除共享的写目标。** 问：这些参与者需要同一个规范对象，还是在发布各自独立的事实？给每个参与者自己拥有的文件、键、分支或状态目录，只在读取/汇报的边界合并。两个 worker 把各自的 `lastX` 字段写进同一个 `state.json` 仍然是共享修改。`indexer-state.json` 加 `metrics-state.json` 就不是。
3. **只有当单一共享写目标是一个真实不变量时，才在结构上串行化访问**（锁文件、顺序阶段、单写者参与者，或原子的 compare-and-swap）。把「我们需要一把锁」当作要检查的设计坏味道，而不是默认答案。
