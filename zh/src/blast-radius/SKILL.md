# Blast radius

在改动上线之前，找出它会弄坏别处的什么。用于 "blast radius of X"、"what could this break"，或审查一个你还不信任的小 diff。当任务简报对既有代码下了断言（"把端点 X 公开"）时，在设计之前就要跑，而不是等到上线前：断言只是假设，调用方普查才是决定设计的那个东西。

与 `how` 和 `why` 互补。`how` 告诉你代码做什么，`why` 告诉你它为什么长这样，blast radius 告诉你它会弄坏别处的什么。

列出调用方不是重点。那些代理一秒钟就能 grep 出来。重点是 grep 给不了你的破坏面。

## Don't trust your own writeup

一份听起来很有道理的爆炸半径分析毫无价值。无论真假它读起来都很可信。所以别交回一份文字报告。找出整件事依赖的一两个事实，靠运行代码把它们证明出来。

### How sure are you

对改动安全所依赖的每个事实，在成本允许的前提下尽可能走到下面列表的深处，并说明停在了哪一层。

1. 你是这么说的。单独来看毫无价值。
2. 你指出了那一行。真实的 `file:line`，或库自己的源码。
3. 你论证了坏情况不会发生。你逐步走过失败路径，它走不到。
4. 你跑过了。一个调用真实代码的脚本或测试，你错了它会大声失败。
5. 你在运行中的应用里复现了。

第 4 步通常就是一个小区脚本：导入应用实际打包的同一个库，调用你担心的那个函数。

## Steps

1. 读改动。diff、它新增/修改/删除的符号、它现在行为的不同之处——包括 diff 没写明的那部分。拉下 PR 和它的 commits。
2. 找出它之所以安全的那个唯一事实。大多数看似危险的改动其实安全，靠的是单一事实，比如"这个调用只清除已经死亡的缓存条目，不做别的"。找到那个事实。它成立的话，大多数危险情形一次性全部排除。把时间花在这里，而不是一长串"可能有问题"。
3. 看 grep 停下的地方。读你调用的库的源码，核对其固定版本和本地补丁。想清楚东西什么时候运行：微任务、卸载和清理、Solid 与 React 的差异。追符号搜索追不到的东西：API 返回的 JSON、数据库列、线上格式、另一种语言读同一批字节、feature flag、下游三跳之外的代码。
4. 对每个风险诚实。给它真实的发生概率和真实的代价。你确认过的风险保留。查过且排除的单独列出。引用真实的 `file:line`——搜索一无所获也是一种答案——绝不编造调用方或 API。
5. 证明那个唯一事实。写一个跑真实代码的脚本或测试，跑它，把发生的事贴出来。
6. 大改动或影响面宽的改动，按 `arena` 跑。把同一个问题抛给多个模型，合并答案。不同模型能抓到不同的真实 bug。

## What to hand back

- **What it does.** 改了什么，包括不那么显眼的部分。
- **The one fact it's safe because of.** 说出来，说明走到了哪一层，展示证据。没能证明就写 unproven。
- **Risks.** 每条写清怎么坏、`file:line`、概率多大、代价多重、怎么核实。要紧的那几条贴上证据。
- **Cleared.** 查了什么、为什么没问题。
- **Before you merge.** 能抓住真实 bug 的最便宜的测试或复现，包括你写的脚本。

全文过 `unslop`，引用真实代码，进入任何公开场合前清掉私有信息。

**Reply:** 上面的报告，那个唯一的安全事实要么已证明，要么标 unproven。
