# Blast radius

在改动上线前，找出它会破坏的其他地方。用于「X 的 blast radius」「这会破坏什么」，或审查一个你还不信任的小 diff。当简报对现有代码做出断言（「把端点 X 设为 public」）时，在设计之前就跑它，而不只是上线前：断言只是假设，调用方普查才是决定设计的依据。

`how` 和 `why` 的同伴技能。`how` 告诉你代码做什么。`why` 告诉你它为什么长这样。Blast radius 告诉你它会在别处破坏什么。

列出调用方不是这份工作。代理一秒就能 grep 出来。这份工作是找到 grep 给不了你的破坏。

## 不要相信你自己写的报告

一份听起来合理的 blast-radius 报告毫无价值。无论真假它都读起来令人信服。所以不要交回报告本身。找出整份报告依赖的一两个事实，通过运行代码证明它们。

### 你有多确定

对改动安全性依赖的每一个事实，尽可能廉价地把它推到下面列表的更深处，并说明它停在哪一步。

1. 你说的。本身毫无价值。
2. 你指出了那一行。真实的 `file:line`，或库自己的源码。
3. 你展示了坏情况不会发生。你一步步走过失败路径，它走不到。
4. 你运行了它。一个脚本或测试，调用真实代码，你错了就大声失败。
5. 你在运行中的应用里复现了它。

第 4 步通常是一个小脚本：导入应用发布时用的同一个库，调用你担心的那个函数。

## 步骤

1. 读改动。diff、它新增、修改和删除的符号、以及它现在行为有何不同，包括 diff 没有明说的部分。用 `why` 的第 2 步拉取 PR 和提交。
2. 找到它因之安全的那一个事实。看起来有风险的改动，大多因为一个单一事实而安全，比如「这次调用只会删掉已经死掉的缓存条目，不做别的」。找到那个事实。它成立的话，大多数风险情形一次性清空。把时间花在这里，而不是一长串「可能」上。
3. 看 grep 停下的地方。读你调用的库的源码，检查它固定的版本和任何本地补丁。弄清事情何时运行：微任务、卸载与 teardown、Solid 还是 React。追踪符号搜索漏掉的东西：API 返回的 JSON、数据库列、线上格式、读取同样字节的另一种语言、feature flag、下游三跳的代码。
4. 对每个风险诚实。给出它真实的发生概率和真实的出错代价。保留你确认的风险。单独列出你查过并排除的。规则同 `why`。引用真实的 `file:line`；一次没有结果的搜索也是一个答案；绝不编造调用方或 API。
5. 证明那一个事实。写一个运行真实代码的脚本或测试，运行它，贴出发生了什么。
6. 对大的或宽泛的改动，作为 `arena` 运行。问多个模型同一个问题，合并答案。不同模型抓到不同的真实 bug。

## 交付什么

- **它做了什么。** 改了什么，包括不明显的部分。
- **它因之安全的那一个事实。** 陈述它，说明推到了哪一步，出示证明。证明不了就写 unproven。
- **风险。** 每条写明如何破坏、`file:line`、多大概率多严重、怎么验证。对重要的几条贴出证明。
- **已排除。** 你查过什么、为什么没问题。
- **合并之前。** 能抓到真实 bug 的最便宜的测试或复现，包括你写的脚本。

通过 `unslop` 写出来，引用真实代码，在它走向任何公开场合之前剥掉一切私密信息。

**回复：** 上面的报告，那一个安全事实要么已证明、要么标记为 unproven。
