# Maintain a verification skill

在 Codex 上，先阅读[平台映射](../poteto-mode/references/codex-tools.md)（包括其中的各技能说明），再执行本技能。

在 GitHub Copilot 上，先阅读[平台映射](../poteto-mode/references/copilot-tools.md)（包括其中的各技能说明），再执行本技能。

在 Muse 上，先阅读[平台映射](../poteto-mode/references/muse-tools.md)（包括其中的各技能说明），再执行本技能。

在 Antigravity 上，先阅读[平台映射](../poteto-mode/references/agy-tools.md)（包括其中的各技能说明），再执行本技能。

应用一变，功能地图立刻开始腐烂。本技能是 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）的维护循环。严谨的单位是功能，不是每一句话：每个功能文件都有源码覆盖、每个功能都实际跑过，但不必把每一条要点都验证到死。

## 结果

选一个，并说明是哪个：

- **clean** — 每个功能都完成了源码覆盖和实跑覆盖；没有值得发布的东西。不开分支，不开 PR。
- **changed** — 一个 PR 发布经过证实的文档、harness 或地图修正。
- **blocked** — 覆盖无法完成，或经证实的修复无法安全发布。准确说明卡在哪。

## 编辑范围

只编辑验证技能自己的目录（它的 SKILL.md、features/，以及它拥有的 harness 脚本）。运行期间绝不编辑产品代码：地图描述的某个行为应用已经不做了，要么是文档漂移（修地图），要么是产品回归（报告它，不要在文档里遮掩）。

## 流程

0. **定位目标。** 找到要维护的验证技能：正文带有启动/驱动章节和功能地图的项目本地技能（`.claude/skills/verify/`，或老版本生成器的 `.claude/skills/verify-*/`）。多个候选就问选哪个；一个都没有就停下，指向 `/create-verification-skill`，不要凭空造目标。

1. **索引卫生。** 读功能地图 README，glob 同目录的其余文件。修掉缺失、多余、重复或失效的条目。轻量操作，不生成清单。

2. **源码波次。** 每个功能文件启动一个只读子代理，并发执行。每个都从源码回答「这个面向用户的功能是怎么工作的？」，带引用标记可能的文档漂移，并返回一份简洁的实跑验证配方。子代理绝不驱动应用，也绝不编辑文件。返回格式：功能摘要 / 源码入口 / 可能的漂移或无 / 一份配方。

3. **对账。** 每个功能文件都要拿到返回的摘要。把重叠的配方合并成尽量少的应用状态。抽查有引用的漂移，干净的结论不必重新证明。扫一遍最近的改动，找地图上缺失的面向用户的表面——认定缺失前必须给出具体的源码路径。

4. **实跑波次。** 即使源码看起来干净也必须做。协调者掌握全部驱动；遵循验证技能自己的启动模型——服务器和 UI 用一个长驻实例串行驱动，短命 CLI 每次驱动开一个全新的隔离会话（由该技能的 Launch 章节决定，不是本技能）。每个功能至少跑一次，整个波次期间守住三条不变量，无论失败是什么：(1) 绝不驱动一个自上次做出意外行为后没做过健康检查的实例——首次驱动前先 doctor，以会话为单位的地方每个新会话 doctor，任何一次驱动失败后再 doctor；doctor 看不出失败时（健康进程上的 UI 卡死状态），重置到已知状态或重启，不要心存侥幸；(2) 已采集的证据要在每次清理后幸存，在它登记的位置核实，不能想当然；(3) 驱动启动的任何东西都不能比这次驱动的用处活得久——失败迭代的残留无论会话是卡住、退出还是共享都要清理（共享实例清的是残留，不是实例本身）。由技能漂移导致的 doctor 失败就是漂移：按编辑范围修掉，重试一次——重启被修复所失效的东西，仅此而已——之后才可以把波次标记为 `blocked`。某个功能够不到，只有在给出具体前置条件（认证、权限、操作系统、外部状态）和已尝试的路线时才标 `verified-unreachable`；地图漏了这个前置条件就是漂移。分诊中产生的任何 harness 修复，发布前都要实跑重验一次。最终收尾在本次运行最后一次驱动之后——包括那些重新证明——保证没有任何东西比本次运行活得久（证据按该技能保留）。

5. **分诊。** 用户视角的描述错了或缺了 → 文档漂移，修掉。harness 驱动不了实际存在的行为 → harness 缺口，修掉；harness 修复遵循与生成时相同的 helpers 规则（脚本可执行、调用方式写进技能正文）。应用行为真的坏了 → 产品缺口；为用户记录下来，但不进这个 PR。

6. **发布或收手。** changed：一个 PR 装经过证实的修正，先重读每个改动过的文件。clean 或 blocked：不开 PR，如实报告结果和覆盖情况。

把简明的运行笔记（覆盖的功能、够不到的前置条件、确认的漂移、结果）放在一个草稿位置；不提交它们。
