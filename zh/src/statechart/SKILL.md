# Statechart

图展示系统如何在状态之间迁移，用的是读图者的语言。那个人——读者——决定行为是否正确。

## 运行

在仓库之外的临时目录里工作。写一个 TLA+ spec 和它的 config。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，所以用一个能执行 TypeScript 的运行时来跑它。

第一次运行会用 mise 安装 TLC 和 Java，需要联网。

## 写 spec

- 把读者认可的每条规则写成一个 INVARIANT。规则可以关于一个界面、一个结果、一个存储值或一条消息。如果模型没有该规则需要的变量，就加变量。绝不为让规则成立而削弱规则。
- 把 `Next` 写成各个动作的析取，比如 `YouPressPlay \/ YouPressStop`。否则 TLC 会把每一步都命名为 `Next`。
- 没有出边的状态会违反 `NoDeadlock`，即使它是正确的终态也一样。当 INVARIANT 或 PROPERTY 已经占用那个名字时，该规则是 `CHECK_DEADLOCK`。往 `Next` 里加一个只在终态为真且不改变任何东西的动作，比如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 里给它一个标签。

## 写图

需要判断力的工作由你来做：每个状态和箭头上的文字、各阶段及其颜色、标题，以及给读者的报告。把你的工作放进一个 view 模块，用 `--view` 传入。

为了呈现读者语言，view 导出 `state(vars)`。`state()` 返回值的类型决定图的形态：

- 字符串给出扁平图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组给出父状态：`export const state = (v) => v.main.split(".");`
- 对象为每个键给出一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

用读者能看到或关心的东西来标记每个状态，比如「Paying」或「Lease held, write pending」。不要把变量名放进标签。在 `vars` 里，TLA+ 序列是键从 1 开始的对象，所以 `v.pc[1]` 是 `pc[1]`。集合是数组。

view 还可以导出 `step(action, from, to)`。它拿到 TLC 动作名和该步前后的值，返回箭头的标签。把每步标签写成用户看到的情形，比如「you press play」或「the connect fails」。不要提代码或 TLA+ 动作名。在图中终点相同的两个动作得到相同标签，从而共享一条箭头。

当某步只在某些条件下发生时，在标签末尾用方括号写上条件，用读者的话，比如 `you press play [while the file loads]`。在区域图中，命令会把条件写在箭头上其他区域的标签文字里，比如 `[when Offline]`。你的方括号会覆盖它，于是来自同一状态的两条箭头可能看起来一样。所以在区域图里，不要为其他区域上的条件写方括号。当一个没有任何标签显示的值决定某步的去向时，在标签里说出结果，比如「the roster read fails」。

view 还可以导出这些：

- `group(vars)` 返回阶段名。每个图状态获得其所属组的颜色。当同一个图状态背后的模型状态分属不同组时，该状态不着色。
- `colors` 给每个组名一个颜色类。
- `title` 是图表顶部显示的字符串。

命令对每个模型状态至多调用一次 `state()` 和 `group()`，对每一步至多调用一次 `step()`。图和报告都使用这些返回值。所以让每个函数只依赖它的参数。

图不画停留在同一标签内的步骤。当读者必须看到这种步骤时，拆分标签。

目标控制在 20 条箭头以内，因为更满的图难以阅读。先从 `state()` 返回更粗的标签。把行为相同的值归入一个标签，省掉读者不需要的细节，比如一个在途且返回值无关紧要的调用。保留 bug 路径上的每个状态，保留每个标记。当合并把一个 `breaks` 状态变成 `mayBreak` 时，它会掩盖规则在哪里被违反。不要合并违反不同规则的两个状态，否则读者无法看出哪条规则在哪里被违反。如果图仍然太满，对读者不需要的步骤从 `step()` 返回 `null`，比如每个状态都有的 reset，或箭头重复其他箭头信息的步骤。隐藏步骤时遵守这些规则：

- 保持每个图状态都能从起始状态经箭头到达。
- 模型中有出步的每个图状态，至少保留一条出箭头。
- 一条箭头的步骤要么全隐藏，要么全保留。只隐藏一部分会让它的条件变窄。
- 在交付说明中写明图隐藏了哪些步骤。

## 读报告

- 图中，违反规则的状态带 `breaks` 类。当只有它背后部分模型状态违反规则时，带 `mayBreak` 类。图例说明每个标记对应的规则。两条规则同时被违反时，一个标记上写出两者，所以在交付说明里讲清哪个状态违反哪条规则。在区域图中，当一个状态所在的每种区域状态组合都能违反某条规则时，该状态获得标记。当某个组合能违反规则而它的任何状态都没有标记时，该组合中的每个状态都获得标记。
- TLC 会越过违反规则的状态继续，所以图会展示 bug 之后的状态。
- 因为 TLC 会越过 bug，一个对状态数没有限制的模型可以无限运行。把常量保持很小，或加一个 CONSTRAINT。
- 使用 VIEW 或 SYMMETRY 时，TLC 把它视为相同的状态计为一个状态，图画那一个状态。箭头可能指向它而非该步真正到达的状态，报告会说明这一点。
- TLC 会对每个越过 CONSTRAINT 或 ACTION_CONSTRAINT 的状态检查规则，但它不会探索该状态，也不检查它是否死锁。当 TLC 为某条规则找到的最短路径终止于这类状态时，图画出该状态，报告给出该路径。图不画出越界之后的其他状态。这类状态里的死锁不会显示。TLC 还会对被 ACTION_CONSTRAINT 排除的每一步之后检查规则，即使下一步是通过其他方式到达的。当 TLC 为某条规则找到的最短路径以这样一步结束时，图画出该步。
- 命令用 TLC 按原样书写的 config 检查规则，单 worker。当一条规则被违反时，命令移除该规则并重跑 TLC，直到没有规则被违反。第一次违反之后，每次运行在 100,000 个不同状态处停止，以免大模型无限运行。当运行到达该上限或因错误停止时，报告在「Rules not checked」下列出未检查的规则，图也不标记它们。未检查的规则可能成立也可能被违反。要检查它，就把被违反的规则从 config 中移除，或把模型变小。该上限会附加一个改变 TLC 变量顺序的模块，所以对属性而言，TLC 可能找到与无上限运行不同的反例。
- `tlc.out` 是 TLC 按原样 config 打印的内容。当图没有展示某条被违反规则的 bug 路径时，`tlc-RULE.out` 是找到它的那次运行打印的内容。当 TLC 重复它的第一条警告时，原生 TLC 会打印两次，但 `tlc.out` 只显示一次，因为 TLC 在本命令读取的输出中省略了第二份。这只有在 Java 以 `-XX:+UseParallelGC` 运行时发生，否则 TLC 的第一条警告是它建议传该标志的提示，只打印一次。

## 展示图

把 `chart.mmd` 以 `mermaid` 代码块展示给用户。图的预算是 500 个状态，按 TLC 在原样 config 上的计数。超过预算时，图只画通往被违反规则的路径；当没有规则被违反时，命令不写 `chart.mmd`。它仍然检查每条规则，报告给出状态数和每条 bug 路径。要看全图，把模型变小。

用 Pele 渲染图。当用户要图片，或图大到文本读不了时，遵循 `references/render.md`。除非用户要求，不要用别的渲染器。

## 交付

把每张图和它的 Mermaid 文本交给必须做判断的人。每个 bug 加一行：规则名、该规则对应的读者语言句子，以及按报告编号的路径。说明模型省略了什么。给出能重新生成这些文件的命令，用新的 `--out` 目录。

当模型描述的是代码时，把每条 bug 路径对着真实代码逐步重放，作为测试或现场复现，每个动作对应一步。如果某个 bug 没有发生，先认为模型是错的，直到你证明它不是。
