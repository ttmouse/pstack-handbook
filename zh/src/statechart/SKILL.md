# Statechart

图展示系统如何在状态之间迁移，用的是读图人的语言。那个人——读者——决定行为是否正确。

## 运行

在仓库外的临时目录里工作。写一个 TLA+ spec 和它的 config。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，所以要用能执行 TypeScript 的运行时来跑。

第一次运行会用 mise 安装 TLC 和 Java，需要联网。

## 写 spec

- 把读者认可的每条规则写成一个 INVARIANT。规则可以关于一个屏幕、一个结果、一个存储值或一条消息。如果模型没有规则对应的变量，就加这个变量。绝不要为了让规则成立而削弱规则。
- 把 `Next` 写成动作的析取，比如 `YouPressPlay \/ YouPressStop`。不这样写的话，TLC 会把每一步都命名为 `Next`。
- 没有出边的状态会违反 `NoDeadlock`，即使它是一个正确的终态。当某个 INVARIANT 或 PROPERTY 已经占用了这个名字，规则就写成 `CHECK_DEADLOCK`。往 `Next` 里加一个只在终态为真且不改变任何东西的动作，比如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 里给它一个标签。

## 选图

需要判断力的工作由你来做：每个状态和箭头上的文字、阶段和它们的颜色、标题，以及给读者的报告。把你的工作放进一个 view 模块，用 `--view` 传入。

要展示读者视角的文字，view 导出 `state(vars)`。`state()` 返回的值决定形式：

- 字符串给出扁平图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组给出父状态：`export const state = (v) => v.main.split(".");`
- 对象给出每个键一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

每个状态的标签写读者能看到或关心的东西，比如"Paying"或"Lease held, write pending"。标签里不要出现变量名。在 `vars` 里，TLA+ 的 sequence 是键从 1 开始的对象，所以 `v.pc[1]` 就是 `pc[1]`。set 是数组。

view 还可以导出 `step(action, from, to)`。它拿到 TLC 的动作名和这一步前后的值，返回箭头的标签。每条 step 标签都写成用户看到它发生的样子，比如"you press play"或"the connect fails"。不要写代码名或 TLA+ 动作名。两个在图里终点相同的动作拿到同一个标签，这样它们共用一条箭头。

当一步只在某些条件下发生时，在标签末尾用方括号写条件，用读者的话，比如 `you press play [while the file loads]`。在区域图里，命令会把条件写在箭头上其他区域的旁边，用它们标签的话，比如 `[when Offline]`。你的方括号会替换它，于是从一个状态出发的两条箭头可能看起来一样。所以在区域图里，不要为另一个区域上的条件写方括号。当一个标签没有显示的值决定了一步走向哪里时，在标签里说出结果，比如"the roster read fails"。

view 还可以导出这些：

- `group(vars)` 返回一个阶段的名字。每个图状态拿它所属组的颜色。当同一个图状态背后的模型状态分属不同的组，这个状态就不上色。
- `colors` 给每个组名一个颜色 class。
- `title` 是一个字符串，图显示在顶部。

命令对每个模型状态最多调用一次 `state()` 和 `group()`，对每一步最多调用一次 `step()`。图和报告都用这些答案。所以让每个函数只依赖自己的参数。

图不画停留在同一个标签里的步骤。当读者必须看到这样的步骤时，拆分标签。

目标是大约 20 条箭头以内，因为更密的图难读。先让 `state()` 返回更粗的标签。把行为相同的值合并成一个标签，略去读者不需要的细节，比如一个在途但对返回值没有影响的调用。保留 bug 路径上的每个状态，保留每个标记。当一次合并把 `breaks` 状态变成 `mayBreak`，它会掩盖规则在哪里被打破。不要合并打破不同规则的两个状态，否则读者就看不到哪条规则在哪里被打破。如果图还是太密，对读者不需要的步骤从 `step()` 返回 `null`，比如每个状态都有的 reset，或者箭头重复其他箭头信息的步骤。隐藏步骤时遵守这些规则：

- 保留每个图状态都能从起始状态沿箭头到达。
- 模型里有出边的每个图状态，至少保留一条出边。
- 一条箭头的步骤要么全藏，要么全不藏。只藏一部分会让它的条件变窄。
- 在交接说明里讲清楚图隐藏了哪些步骤。

## 读报告

- 图里，打破规则的状态有 `breaks` class。当它背后只有一部分模型状态打破该规则时，有 `mayBreak` class。Legend 写明每个标记对应的规则。两条规则都打破时，同一个标记上写出两条，所以要在交接说明里讲清哪个状态打破哪条规则。在区域图里，当一个状态所在的每种区域状态组合都可能打破某条规则时，它拿到标记。当某个组合可能打破规则而它的任何状态都没有标记时，组合里的每个状态都拿到标记。
- TLC 会越过打破规则的状态继续走，所以图会显示 bug 之后的状态。
- 因为 TLC 会越过 bug，一个状态数没有上限的模型可能无限运行。把常量调小，或加一个 CONSTRAINT。
- 用了 VIEW 或 SYMMETRY 时，TLC 把它视为相同的状态算作一个，图画的也是那一个。箭头可能指向它而不是步骤真正到达的状态，报告会说明这一点。
- TLC 会检查 CONSTRAINT 或 ACTION_CONSTRAINT 之后每个状态的规则，但不探索该状态、不检查死锁。当 TLC 对某条规则的最短路径终点落在这样的状态上，图画出该状态，报告给出那条路径。图不画出界之外的其他状态。这种状态里的死锁不会显示。ACTION_CONSTRAINT 排除的每一步之后 TLC 也会检查规则，即使下一步可以通过别的路径到达。当 TLC 对某条规则的最短路径以这样一步结束时，图画出这一步。
- 命令用 TLC 按原样的 config 检查规则，单 worker。当一条规则被打破，命令移除该规则再跑 TLC，直到没有规则被打破。第一次打破之后，每轮运行在 100,000 个不同状态处停止，防止大模型无限跑。当一轮运行到达该界或因错误停止，报告在"Rules not checked"下列出没有检查的规则，图也不给它们做标记。未检查的规则可能成立也可能被打破。要检查它，从 config 里移除被打破的规则，或把模型调小。这个界会附加一个模块来改变 TLC 的变量顺序，所以对 property，TLC 可能找到与不带界的运行不同的反例。
- `tlc.out` 是 TLC 按原样 config 打印的内容。当图没有显示某条被打破规则的 bug 路径时，`tlc-RULE.out` 是找到它的那轮运行打印的内容。当 TLC 重复它的第一条警告时，原生 TLC 会打印两次，但 `tlc.out` 只显示一次，因为 TLC 把第二份从本命令读取的输出里去掉了。这只在 Java 用 `-XX:+UseParallelGC` 运行时发生，否则 TLC 的第一条警告是它建议传该 flag 的提示，只打印一次。

## 展示图

把 `chart.mmd` 用 `mermaid` 代码块展示给用户。图的预算是 500 个状态，按 TLC 在原样 config 上统计。超过之后，图只画到被打破规则的路径，没有规则被打破时，命令不写 `chart.mmd`。它仍然检查每条规则，报告给出状态数和每条 bug 路径。要看完整图，把模型调小。

用 Pele 渲染图。当用户要图片，或图大到文本读不动时，按 `references/render.md` 做。除非用户要求，不要换别的渲染器。

## 交接

把每张图和它的 Mermaid 文本交给要做决定的人。每个 bug 加一行：规则、该规则的读者视角句子、按报告编号的路径。说明模型省略了什么。附上重新生成文件的命令，用一个全新的 `--out` 目录。

当模型描述的是代码时，把每条 bug 路径对着真实代码重放，用测试或现场复现，每个动作一步。如果 bug 没有出现，先假设模型错了，直到你证明它没错。
