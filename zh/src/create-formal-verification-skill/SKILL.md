# 创建一个形式化验证技能

在 Codex 上，先读[平台映射](../poteto-mode/references/codex-tools.md)（包括其中的逐技能说明），再执行本技能。

在 GitHub Copilot 上，先读[平台映射](../poteto-mode/references/copilot-tools.md)（包括其中的逐技能说明），再执行本技能。

在 Muse 上，先读[平台映射](../poteto-mode/references/muse-tools.md)（包括其中的逐技能说明），再执行本技能。

在 Antigravity 上，先读[平台映射](../poteto-mode/references/agy-tools.md)（包括其中的逐技能说明），再执行本技能。

测试只检查有人想到要写的那些用例。形式化验证检查一个既定范围内的所有用例：模型里步骤的每一种顺序、上界之内的每一种输入、或所有输入。本技能找到仓库里这件事最重要的那部分，验证它的一个性质，并留下一个项目本地技能，让下一个代理能拿改动对照这个性质检查。这个技能是写给一个冷读它、正在改代码、从未见过你工作的代理的。用户必须能够信任结果并据此行动，而不需要学那门验证语言。

## 从代码里选目标

答案从代码库里找，只有观察不到的才问用户。如果用户点名了一个区域或一个 bug，从那里开始。

好目标是代码做出的一个承诺：一旦破坏会伤害用户，而测试很少到达破坏它的那个用例。选仓库里最强的一个这样的目标，不是最容易验证的那个。

## 让问题选工具

选以最低成本回答问题的工具：模型检查器、证明助手、基于 SMT 的验证器、或其他工具。「事件能否以坏的顺序发生」通常适合用模型检查器对设计的小模型检查，任何语言下 TLA+ 都是默认选择。「代码本身对每种输入是否表现正确」，比如内存安全、溢出、或数据结构不变量，通常适合跑在代码上的验证器。如果没有验证器跑在这个语言上，就说出来，并用生成的输入测试真实代码，而不是函数的手工模型。一个必须对任意规模成立的性质，上界不够时，可能需要证明。优先选仓库的开发者能安装和运行的工具，并告诉用户你为什么选它。

## 什么算好

- **忠于代码。** 模型或证明的每一部分都指向审阅者能打开的代码。验证当作一个不可分步骤的东西，在代码里就是一个不可分步骤。名字来自这个仓库。
- **能够失败。** 一个你从未见过失败的检查证明不了任何东西。展示每个性质在它所守护代码的破坏变体上失败，比如移除一个检查、调换一步顺序。
- **发现保持为发现。** 当前代码破坏该性质时，用代码的术语连同反例一起报告。不要为了让它通过而削弱性质或模型，用户没让就不改产品代码。
- **对范围诚实。** 说明验证了什么、在哪些界和假设下、留下了什么没覆盖。一次通过覆盖的是模型或界，不是整个系统。
- **不用工具也能读。** 用一句平实的话分别陈述性质和危害。把一个反例讲成用代码的话写成的简短步骤序列。
- **重跑便宜。** 一条命令、可复现的工具版本、短到下一个代理会在每次相关改动上都用它。
- **与代码保持同步。** 记录每个检查覆盖哪些文件和函数，以及你最后一次确认验证描述了它们的 commit。被覆盖的代码在那个 commit 之后变化时，下一个代理能看出验证需要再看一眼。

## 生成形式化验证技能

写一个项目本地技能，frontmatter 里写明区域和使用时机。技能按区域命名，绝不叫 `verify` 或用 `verify-` 前缀，那属于 `/create-verification-skill` 写的 driver 技能。在 Claude Code 上它位于 `.claude/skills/<area>/SKILL.md`。没有 frontmatter，技能永远不会注册。只凭这个技能，下一个代理必须能判断一个改动是否触及被验证的代码、跑检查、把真 bug 和建模错误区分开、并在改动是有意的时候更新验证。把覆盖记录和同步 commit 放进技能，并告诉下一个代理：只有在它确认验证描述了新 commit 上的代码之后，才把同步 commit 往前挪。用这个仓库真实的命令、路径和名词，不留占位符。

如果检查是一个 TLA+ 模型，告诉下一个代理用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能读每一条结果。它把检查器发现的每个不变量违反以其最短路径用平实的话展示出来。检查通过时，`/statechart` 画出系统在状态间怎么移动的图。按名字引用 `/statechart`。它的命令、选项和文件路径在版本和机器之间会变，所以一个也不要复制进生成的技能或它的脚本。

## 交付前先证明

按下一个代理的方式，把生成的技能走一遍：用一个破坏真实代码中该性质的临时改动。它必须抓住这个破坏。然后撤掉临时改动，确认检查回到起点：通过，或只在你将要报告的发现上失败。从未运行过的形式化验证技能是草稿。如果技能漏掉了破坏，或某一步没跑起来，修技能或修验证，不是修临时改动。

## 交接

告诉用户你验证了什么、用了哪个工具以及为什么、界是什么、检查发现了什么（用平实的话）、怎么跑、它不覆盖什么。只有找到一个很近的目标时才建议第二个目标。把 `/maintain-formal-verification-skill` 指给用户，用于在没有被重新检查的改动之后把验证拉回正轨。
