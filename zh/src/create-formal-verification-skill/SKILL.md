# Create a formal verification skill

在 Codex 上，遵循本技能前先读[平台映射](../poteto-mode/references/codex-tools.md)，包括其中按技能给出的说明。

在 GitHub Copilot 上，遵循本技能前先读[平台映射](../poteto-mode/references/copilot-tools.md)，包括其中按技能给出的说明。

在 Muse 上，遵循本技能前先读[平台映射](../poteto-mode/references/muse-tools.md)，包括其中按技能给出的说明。

在 Antigravity 上，遵循本技能前先读[平台映射](../poteto-mode/references/agy-tools.md)，包括其中按技能给出的说明。

测试检查的是有人想到要写的那些用例。形式化验证检查的是既定范围内的每一个用例：模型里步骤的每一种顺序、上界之内的每一个输入，或全部输入。本技能找出仓库里这件事最要紧的部分，验证它的一个性质，并留下一个项目本地的技能，让下一个代理能拿改动对照这个性质。这个技能要写给一个冷启动、改到一半才读它、从没见过你工作的代理。用户必须能够信任结果并据此行动，而不需要学那门验证语言。

## Choose the target from the code

答案从代码库里来，只有观察不到的才问用户。如果用户指了某个区域或某个 bug，从那里开始。

好目标是一个代码做出的承诺：一旦破坏会伤害用户，而测试很少能跑到破坏它的那个用例。选仓库里最强的这样的目标，不是最容易验证的那个。

## Let the question choose the tool

选以最低成本回答问题的工具：模型检查器、证明助手、SMT 后端的验证器，或其他工具。"事件会不会以坏的顺序发生"这类问题通常适合对设计的小模型做模型检查，任意语言下 TLA+ 都是默认选择。"代码本身对每个输入是否正确"——比如内存安全、溢出、数据结构不变量——通常适合直接跑在代码上的验证器。如果这门语言没有能跑的验证器，就直说，并用生成的输入去测真实代码，而不是对函数的手工建模。一个必须在任意规模下都成立的性质，上界不够用时可能需要证明。优先选仓库的开发者能安装、能运行的工具，并向用户说明选择理由。

## What makes it good

- **忠于代码。** 模型或证明的每个部分都指向评审者可以打开的代码。验证当作一个不可分割步骤的东西，在代码里也是一个不可分割的步骤。命名来自这个仓库。
- **能够失败。** 一条你从没见过失败的检查证明不了任何事。展示每个性质在其守护代码的坏变体上失败，比如删掉一处检查或调换两步顺序。
- **发现就是发现。** 当前代码破坏性质时，就用代码的语言连同反例一起报告。不要为了让它通过而削弱性质或模型，除非用户要求也不要改产品代码。
- **对范围诚实。** 说清验证了什么、在哪些上界和假设下、漏掉了什么。一次通过覆盖的是模型或上界，不是整个系统。
- **不装工具也能读。** 性质和危害各用一句大白话说清。反例用代码的语言讲成一串简短的步骤。
- **重跑成本低。** 一条命令、可复现的工具版本、运行时长短到下一个代理在每次相关改动上都愿意跑。
- **与代码保持同步。** 记录每条检查覆盖的文件和函数，以及你最后一次确认验证仍描述这些代码的 commit。被覆盖的代码在那之后变了，下一个代理就能看出验证需要重新审视。

## Generate the formal verification skill

写一个项目本地的技能，frontmatter 说明区域和使用时机。技能按区域命名，绝不用 `verify` 或 `verify-` 前缀——那属于 `/create-verification-skill` 写出的驱动技能。在 Claude Code 上放在 `.claude/skills/<area>/SKILL.md`。没有 frontmatter，技能永远不会注册。下一个代理仅凭这个技能就要能判断：一个改动是否碰到被验证的代码、怎么跑检查、怎么区分真 bug 和建模错误、以及改动是有意为之时怎么更新验证。把覆盖记录和同步 commit 写进技能，并告诉下一个代理：只有在确认验证描述了新 commit 上的代码之后，才能把同步 commit 前移。用这个仓库真实的命令、路径和名词，不留占位符。

如果检查是 TLA+ 模型，告诉下一个代理用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能读每份结果。它把检查器发现的每个不变量违例以其最短路径的大白话呈现。检查通过时，`/statechart` 会画出系统在状态间如何流转的图。按名字引用 `/statechart`。它的命令、选项和文件路径随版本和机器变化，所以不要把任何一个抄进生成的技能或其脚本。

## Prove it before you hand off

按下一个代理的方式，对真实代码里一个破坏该性质的临时改动，完整走一遍生成的技能。它必须抓到这个破坏。然后撤掉临时改动，确认检查回到原点：通过，或只在你将要报告的那些发现上失败。从没跑过的形式化验证技能只是一份草稿。如果技能漏掉了破坏或某一步跑不起来，修技能或修验证，不是修临时改动。

## Hand off

告诉用户验证了什么、用了哪个工具以及为什么、上界是什么、检查发现了什么（大白话）、怎么跑、以及它不覆盖什么。只有确实找到下一个相近目标时才顺带建议。用户在改动之后没有重新验证、验证偏离了代码时，指引他们去 `/maintain-formal-verification-skill`。
