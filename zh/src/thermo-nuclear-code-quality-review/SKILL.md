# Thermo-Nuclear Code Quality Review

本技能用于一次格外严格的评审，聚焦实现质量、可维护性、抽象质量和代码库健康度。

最重要的是，本技能要推动评审者对代码结构保持**雄心**。不要只找出局部的清理机会。主动寻找"code judo"式操作：在保持行为不变的前提下，让实现戏剧性地更简单、更小、更直接、更优雅的重构方案。

## 核心提示词

从这条基线出发：

> 对当前分支的改动做一次深度代码质量审计。
> 重新思考如何组织、实现这些改动，在不影响行为的前提下实质性提升代码质量。
> 改进抽象和模块化，减少 Spaghetti 代码，提升简洁度和可读性。
> 要有雄心。如果有一条清晰的路能通过重构部分代码库来改进实现，就去做。
> 极度彻底、极度严谨。三思而后行，一次裁对。

## 不可妥协的附加标准

应用上面的基线提示词，外加这些明确的评审规则：

0. **对结构简化保持雄心。**
   - 不要停在"这里可以再干净一点"。
   - 寻找重新框定改动的机会，让整块分支、辅助函数、模式、条件层彻底消失。
   - 优先选择那种事后回看显得必然的方案。
   - 假设通常存在一步"code judo"：一次更有效利用现有架构的重组织，让改动戏剧性地更简单、更优雅。
   - 如果你看到一条能删除复杂度而非搬移复杂度的路径，强烈推动那条路径。

1. **不允许一个 PR 把文件从 1k 行以下推到 1k 行以上，除非有非常强的理由。**
   - 默认把这种情况视为强烈的代码质量坏味道。
   - 优先抽取辅助函数、子组件、模块或局部抽象，而不是放任文件膨胀过 1000 行。
   - 如果 diff 跨过了这条线，明确追问是否应该先拆分。
   - 只有存在压倒性的结构理由、且拆完之后文件仍然组织清晰时才可豁免。

2. **不允许既有代码里随机滋长意大利面。**
   - 对新塞进无关流程的临时条件、散落的特例、一次性分支保持高度警惕。
   - 如果一个改动加了"到处乱插的怪 if"，把它当作设计问题，而不是风格小疵。
   - 优先把逻辑推进专门的抽象、辅助函数、状态机、策略对象或独立模块，而不是缠住现有路径。
   - 点名让周边代码更难推理的改动，即使它在技术上能跑。

3. **倾向于清理设计，而不是无条件接受能跑的代码。**
   - 如果行为可以保持不变而结构能显著变干净，推动更干净的版本。
   - 不要给"能跑就行"的实现盖章，留下一地狼藉。
   - 强烈优先彻底移除活动部件的简化，胜过只是把同样的复杂度摊开的重构。

4. **偏好直接、朴素、可维护的代码，而不是 hack 或魔法代码。**
   - 把脆弱的、临时拼凑的、"魔法"的行为当作代码质量问题。
   - 对隐藏简单数据结构假设的泛型机制保持怀疑。
   - 点名薄抽象、恒等包装、纯转发的辅助函数——加了间接层却没换来清晰度。

5. **当类型和边界影响可维护性时，狠狠收紧它们。**
   - 在存在更清晰类型边界的情况下，追问不必要的可选性、`unknown`、`any` 或到处转型。
   - 优先显式的类型化模型或共享契约，而不是松散的临时对象。
   - 如果一个分支靠静默兜底掩盖一个不清晰的不变量，追问是否应该把这个边界显式化。

6. **逻辑留在它该在的层，复用已有的辅助函数。**
   - 点名功能逻辑泄漏进共享路径，或实现细节穿过 API 渗出。
   - 优先用既有的正规工具函数，而不是自造一次性版本。
   - 把代码推向正确的包、服务或模块，而不是把架构漂移常态化。

7. **当更干净的结构显而易见时，把不必要的串行编排和非原子更新当作设计坏味道。**
   - 如果独立的工作没有理由地被串行化，追问流程是否应该并行。
   - 如果相关更新可能把状态留在只改了一半的样子，推动更原子的结构。
   - 不要钻微优化的牛角尖，但要点名那些让实现更脆弱、且本可避免的编排复杂度。

## 核心评审问题

对每个有分量的改动，问：

- 有没有一步"code judo"能让它戏剧性地变简单？
- 能不能换个框定方式，让概念、分支或辅助层变少？
- 这是在改善还是恶化局部架构？
- diff 是不是在本该有更好抽象的地方加了分支复杂度？
- 之前内聚的模块是否变得更耦合、状态更多、更难扫读？
- 这段逻辑待在正确的文件和层里吗？
- 这个改动是否把某个文件或组件撑过了健康的尺寸边界？
- 有没有重复出现的条件在暗示缺一个模型或缺一个辅助函数？
- 实现是直接、可读的，还是依赖特例和偶然的控制流？
- 这个抽象真的物有所值，还是只是一个包装？
- diff 是否引入了掩盖真实不变量的转型、可选性或临时对象结构？
- 这段逻辑待在正规层里吗，还是 diff 把细节泄漏过了边界？
- 这个编排是否比必要的更串行、更不原子？

## 要激烈点名的问题

看到以下情况就升级：

- 一个复杂实现，而更干净的框定可以整类删除复杂度。
- 只是把代码搬来搬去、却没减少读者脑内概念数的重构。
- 一个文件因 PR 跨过 1000 行，尤其是新代码本可以拆出去时。
- 硬拧到无关代码路径上的新条件。
- 让既有控制流变复杂的一次性布尔、可空模式或 flag。
- 功能专属逻辑泄漏进通用模块。
- 隐藏简单结构、让代码更难推理的泛型"魔法"处理。
- 加了间接层却什么都没简化的薄包装或恒等抽象。
- 让真实契约变浑浊的不必要转型、`any`、`unknown` 或可选参数。
- 复制粘贴的逻辑，而不是抽取辅助函数。
- 塞在已经很忙的函数中段的窄边界情况处理。
- 技术上过测试、但让代码更不模块化更难读的重构。
- 大概率变成永久负债的"临时"分支。
- 代码库里已有正规工具时另造的自用辅助函数。
- 加在错误的层或包里的逻辑，而它本该待在更中心的位置。
- 明显独立的工作本可以用并行执行保持更简单更清晰，却写成串行 async 流。
- 让状态比必要的更不原子的部分更新逻辑。

## 优先的修复建议

发现代码质量问题时，优先提这类建议：

- 删掉一整层间接，而不是打磨它。
- 重新框定状态模型，让条件消失而不是被集中管理。
- 改变所有权边界，让功能自然成为现有抽象的延伸。
- 把特例逻辑变成一条更简单的默认流程，异常更少。
- 抽取一个辅助函数或纯函数。
- 把大文件拆成更小的聚焦模块。
- 把功能专属逻辑挪到专门抽象背后。
- 用类型化模型或显式分发器替换条件链。
- 把编排和业务逻辑分开。
- 把重复分支折叠成一条更清晰的流程。
- 删掉没有实质澄清 API 的包装。
- 复用既有的正规辅助函数，而不是引入近似副本。
- 把类型边界显式化，让控制流跟着变简单。
- 把逻辑挪到已经拥有这个概念的包、模块或层。
- 并行化独立的工作，前提是它同时简化了编排。
- 把相关更新重组为更原子的流程，避免部分状态难以推理。

当真正的问题是结构性的，不要满足于"也许可以重命名一下"级别的反馈。
如果存在一条通往简单得多的方案的可行路径，不要满足于同一个乱想法的更干净版本。

## 评审语气

对质量直接、认真、高要求。
不要粗鲁，但不要把重大的可维护性问题软化成温和的建议。
如果代码正在把代码库弄乱，清楚地说出来。
如果实现错过了一次戏剧性简化的机会，也同样清楚地说出来。

好用的句式：

- `this pushes the file past 1k lines. can we decompose this first?`
- `this adds another special-case branch into an already busy flow. can we move this behind its own abstraction?`
- `this works, but it makes the surrounding code more spaghetti. let's keep the behavior and restructure the implementation.`
- `this feels like feature logic leaking into a shared path. can we isolate it?`
- `this abstraction seems unnecessary. can we just keep the direct flow?`
- `why does this need a cast / optional here? can we make the boundary more explicit instead?`
- `this looks like a bespoke helper for something we already have elsewhere. can we reuse the canonical one?`
- `i think there's a code-judo move here that makes this much simpler. can we reframe this so these branches disappear?`
- `this refactor moves complexity around, but doesn't really delete it. is there a way to make the model itself simpler?`

## 输出预期

按这个顺序给发现排优先级：

1. 结构性的代码质量回退
2. 错过的戏剧性简化机会 / code-judo 重构机会
3. 意大利面 / 分支复杂度的增长
4. 让代码更难推理的边界 / 抽象 / 类型契约问题
5. 文件尺寸与拆分问题
6. 模块化与抽象问题
7. 可读性与可维护性问题

存在更大的结构问题时，不要用低价值的小疵淹没评审。
宁可少量高确信的评论，也不要一长串化妆级别的备注。

## 报告格式

交付物是分层的，绝不是单个巨型文件：

- 把评审写进独立目录（比如 `/tmp/<project>-thermo/`）：一份汇总报告，加上每个子系统或评审者一份详细报告（`01_<subsystem>.md`、`02_<subsystem>.md`……）。
- 汇总要一口气能读完，约 200 行：结论、每条发现一个简短的叙述段、建议的修复顺序，以及指向承载完整证据的细节文件的指引。
- 细节文件承载深度：测量数据、产生数据的命令、验证状态、成型的 code-judo 提案。
- 发现写成散文段落。先点名文件和证据，再用句子解释问题和修复方案。不要把发现压成残句、标签粥或内联命令堆，尤其是汇总里。
- 当评审通过 **swarm** 技能扇出并行评审者时，本节覆盖 swarm 的聚合规则：每位评审者的报告就是交付物的细节文件，不是要丢掉的原始转储。判断综合进汇总；细节留在磁盘上并给出链接。

## 通过标准

不要仅仅因为行为看起来正确就通过。
通过的门槛是：

- 没有明显的结构性回退
- 当更简单的实现路径可见时，没有错过让它戏剧性变简单的明显机会
- 没有无正当理由的文件尺寸爆炸
- 没有来自特例分支的明显意大利面滋长
- 没有明显 hack 或魔法、让代码更难推理的抽象
- 没有用不必要的包装、转型、可选性搅浑真实设计
- 没有清晰的架构边界泄漏或本可避免的正规辅助函数重复
- 没有错过一个能实质改善可维护性的明显拆分机会

以下情况默认视为阻塞项，除非作者能清楚说明正当理由：

- 存在可行的 code-judo 能删掉的偶发复杂度，PR 却把它保留了下来
- PR 把文件从 1000 行以下推到 1000 行以上
- PR 加入的临时分支让既有流程更缠结
- PR 用把功能检查散进共享代码的方式解决局部问题
- PR 加入让设计更绕的多余抽象、包装或重度转型的契约
- PR 重复了已有的辅助函数，或把逻辑放错了层，而它明明有清晰的正规归宿

这些条件不满足时，留下明确、可操作的反馈，推动更干净的拆分。
