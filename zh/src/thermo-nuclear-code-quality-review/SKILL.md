# 热核级代码质量审查

当审查需要格外严格、聚焦实现质量、可维护性、抽象质量和代码库健康度时，使用本技能。

最重要的是，本技能应推动审查者对代码结构保持**雄心**。不要只找出局部清理机会。主动寻找「代码柔道（code judo）」手法：在保持行为不变的前提下，让实现显著更简单、更小、更直接、更优雅的重构。

## 核心提示词

从这个基线开始：

> 对当前分支的改动做一次深度代码质量审计。
> 重新思考如何组织 / 实现这些改动，在不影响行为的前提下切实提升代码质量。
> 改进抽象、模块化，减少面条式代码，提升简洁性与可读性。
> 要有雄心：如果存在一条通过重构部分代码库来改进实现的清晰路径，就去做。
> 极度彻底、极度严谨。三思而后行（量两次，裁一次）。

## 不可妥协的附加标准

应用上面的基线提示词，再加上这些明确的审查规则：

0. **对结构性简化保持雄心。**
   - 不要止步于「这里可以稍微干净一点」。
   - 寻找重新框定改动的机会，让整段分支、辅助函数、模式、条件或层完全消失。
   - 优先选择那种事后看让代码显得理所当然的方案。
   - 假定往往存在一个「代码柔道」手法：一次更有效利用现有架构的重组，让改动显著更简单、更优雅。
   - 如果看到一条删除复杂性而非重新排列复杂性的路径，极力争取那条路径。

1. **不要让一个 PR 把文件从 1k 行以下推到 1k 行以上，除非有非常强的理由。**
   - 默认把这当作强烈的代码质量坏味道。
   - 优先提取辅助函数、子组件、模块或局部抽象，而不是任由文件蔓延超过 1000 行。
   - 如果 diff 越过了这条线，明确追问是否应当先分解代码。
   - 只有存在令人信服的结构性理由且产出的文件仍然组织清晰时，才允许豁免。

2. **不允许既有代码出现随意的面条式增长。**
   - 对新增的临时条件、散落的特例、插入到无关流程中的一次性分支保持高度怀疑。
   - 如果一个改动「在随机位置加入了怪异的 if 语句」，把它当作设计问题，而不是风格瑕疵。
   - 优先把逻辑推进到专属的抽象、辅助函数、状态机、策略对象或独立模块，而不是纠缠现有路径。
   - 指出那些让周边代码更难推理的改动，即使它们在技术上能工作。

3. **倾向于清理设计，而不是接受能跑的代码。**
   - 如果行为可以保持不变而结构能明显更干净，推动更干净的版本。
   - 不要草率盖章那些让代码库更凌乱的「能跑就行」实现。
   - 强烈优先能彻底移除活动部件的简化，而不是仅仅把同样的复杂度摊开的重构。

4. **优先直接、朴素、可维护的代码，而不是取巧或魔法的代码。**
   - 把脆弱、临时或「魔法」的行为当作代码质量问题。
   - 对隐藏简单数据形状假设的通用机制保持怀疑。
   - 标记那些只增加间接层却换不来清晰度的薄抽象、恒等包装或透传辅助函数。

5. **当类型和边界影响可维护性时，对它们严加要求。**
   - 当存在更清晰的类型边界时，质询不必要的可空性、`unknown`、`any` 或重度转型的代码。
   - 优先显式的类型化模型或共享契约，而不是松散形状的临时对象。
   - 如果一个分支依赖静默回退来掩盖不清的不变量，追问是否应当让边界显式化。

6. **把逻辑放在规范层，复用既有辅助函数。**
   - 指出功能逻辑泄漏进共享路径，或实现细节经由 API 泄漏。
   - 优先既有的规范工具/辅助函数，而不是定制的独一份。
   - 把代码推向正确的包、服务或模块，而不是把架构漂移正常化。

7. **当更干净的结构显而易见时，把不必要的串行编排和非原子更新当作设计坏味道。**
   - 如果独立工作无缘由地被串行化，追问流程是否应当并行运行。
   - 如果相关更新可能让状态处于半应用状态，推动更原子的结构。
   - 不要在微优化上过度纠缠，但要标记那些让实现更脆弱、可避免的编排复杂度。

## 主要审查问题

对每一处有意义的改动，问：

- 是否存在能让它显著更简单的「代码柔道」手法？
- 能否重新框定这个改动，让概念、分支或辅助层更少？
- 这是在改善还是恶化局部架构？
- diff 是否在本应有更好抽象的地方增加了分支复杂度？
- 原本内聚的模块是否变得更耦合、状态更多、更难扫读？
- 这段逻辑是否在正确的文件和层里？
- 这次改动是否把文件或组件撑过了健康的尺寸边界？
- 是否有重复出现的条件，暗示缺少一个模型或辅助函数？
- 实现是直接且易读的，还是依赖特例和偶然的控制流？
- 这个抽象真的物有所值，还是只是一个包装？
- diff 是否引入了掩盖真实不变量的转型、可空性或临时对象形状？
- 这段逻辑是否在规范层，还是 diff 跨越边界泄漏了细节？
- 这段编排是否比必要的更串行、更不原子？

## 要猛烈标记的问题

出现以下情况时升级发现：

- 一个复杂的实现，其更干净的重新框定可以删掉整类复杂性。
- 只是把代码挪来挪去、却没有减少读者必须记住的概念数量的重构。
- 一个文件因 PR 越过 1000 行，尤其是新代码本可以拆出去。
- 硬加到无关代码路径上的新条件。
- 让既有控制流变复杂的一次性布尔值、可空模式或开关。
- 泄漏进通用模块的功能专属逻辑。
- 隐藏简单结构、让代码更难推理的通用「魔法」处理。
- 只增加间接层、不简化任何东西的薄包装或恒等抽象。
- 把真实契约搅浑的不必要转型、`any`、`unknown` 或可选参数。
- 复制粘贴的逻辑，而不是提取辅助函数。
- 在本已繁忙的函数中间实现的狭隘边界情况处理。
- 技术上通过测试、却让代码更不模块化或更难读的重构。
- 大概率变成永久债务的「临时」分支。
- 代码库已有规范工具可用的岗位上新写的定制辅助函数。
- 加在错误的层/包里、本应放在更中心位置的逻辑。
- 明显独立的工作本可以用并行执行保持更简单更清晰，却写成了串行异步流程。
- 让状态比必要更不原子的部分更新逻辑。

## 优先的整改方案

识别出代码质量问题时，优先提这类建议：

- 删掉整层间接，而不是打磨它。
- 重新框定状态模型，让条件消失而不是被集中起来。
- 更改所有权边界，让功能成为既有抽象的自然延伸。
- 把特例逻辑变成更简单、例外更少的默认流程。
- 提取辅助函数或纯函数。
- 把大文件拆成更小、更聚焦的模块。
- 把功能专属逻辑移到专属抽象之后。
- 用类型化模型或显式分发器替代条件链。
- 把编排与业务逻辑分离。
- 把重复分支折叠成一条更清晰的流程。
- 删掉对 API 没有实质澄清作用的包装。
- 复用既有的规范辅助函数，而不是引入近似重复。
- 让类型边界更显式，从而让控制流更简单。
- 把逻辑移到已经拥有该概念的包/模块/层。
- 当并行化同时能简化编排时，把独立工作并行化。
- 当部分状态会更难推理时，把相关更新重构为更原子的流程。

当真正的问题是结构性问题时，不要满足于「也许改个名」式的反馈。
如果存在一条通往简单得多的想法的可行路径，不要满足于同一个凌乱想法的仅仅更干净的版本。

## 审查语气

对质量直接、严肃、严苛。
不要粗鲁，但不要把重大可维护性问题软化成温和建议。
如果代码正在让代码库变凌乱，清楚地说出来。
如果实现错过了一次戏剧性简化的机会，也要清楚地说出来。

好的措辞：

- `this pushes the file past 1k lines. can we decompose this first?`
- `this adds another special-case branch into an already busy flow. can we move this behind its own abstraction?`
- `this works, but it makes the surrounding code more spaghetti. let's keep the behavior and restructure the implementation.`
- `this feels like feature logic leaking into a shared path. can we isolate it?`
- `this abstraction seems unnecessary. can we just keep the direct flow?`
- `why does this need a cast / optional here? can we make the boundary more explicit instead?`
- `this looks like a bespoke helper for something we already have elsewhere. can we reuse the canonical one?`
- `i think there's a code-judo move here that makes this much simpler. can we reframe this so these branches disappear?`
- `this refactor moves complexity around, but doesn't really delete it. is there a way to make the model itself simpler?`

## 输出预期

按此顺序排列发现的优先级：

1. 结构性代码质量回退
2. 错失的戏剧性简化 / 代码柔道重构机会
3. 面条式 / 分支复杂度增加
4. 让代码更难推理的边界 / 抽象 / 类型契约问题
5. 文件尺寸与分解问题
6. 模块化与抽象问题
7. 可读性与可维护性问题

如果存在更大的结构性问题，不要让审查被低价值的琐碎意见淹没。
宁可少量高置信度的评论，也不要一长串修饰性备注。

## 报告格式

交付物是分层的，绝不是一个单一的巨型文件：

- 把审查写进自己的目录（例如 `/tmp/<project>-thermo/`）：一份汇总报告，外加每个子系统或审查者一份详细报告（`01_<subsystem>.md`、`02_<subsystem>.md`、…）。
- 汇总保持一次读完的篇幅，约 200 行：结论、每条发现一个简短的叙述段落、一个建议的整改顺序，以及指向承载该发现完整证据的详情文件的指针。
- 详情文件承载深度：测量数据、产出这些数据的命令、验证状态，以及完整的代码柔道提案。
- 发现写成散文段落。先点名文件和证据，再用句子解释问题和整改方案。不要把发现压缩成碎片行、标签堆，或在汇总里内联倾倒命令。
- 当审查通过 **swarm** 技能横向展开并行审查者时，本节覆盖 swarm 的聚合规则：每个审查者的报告就是交付物的详情文件，不是可以丢弃的原始倾倒物。把判断整合进汇总；细节留在磁盘上并链接过去。

## 通过标准

不要仅仅因为行为看起来正确就通过。
通过的标准是：

- 没有明确的结构性回退
- 当通往显著更简单实现的路径可见时，没有明显错失的机会
- 没有无正当理由的文件尺寸爆炸
- 没有来自特例分支的明显面条式增长
- 没有明显取巧或魔法、让代码更难推理的抽象
- 没有掩盖真实设计的多余包装/转型/可空性搅动
- 没有清晰的架构边界泄漏或可避免的规范辅助函数重复
- 没有明显错失的、能切实改善可维护性的分解

除非作者能清楚说明理由，把这些当作推定阻塞项：

- 当存在能删掉附带复杂度的可行代码柔道手法时，PR 却保留了它
- PR 把文件从 1000 行以下推到 1000 行以上
- PR 增加了让既有流程更纠缠的临时分支
- PR 通过把功能检查撒进共享代码来解决局部问题
- PR 增加了让设计更间接的多余抽象、包装或重度转型的契约
- 在存在清晰的规范归属时，PR 重复了既有辅助函数或把逻辑放错了层

如果这些条件不满足，留下明确、可执行的反馈，推动更干净的分解。
