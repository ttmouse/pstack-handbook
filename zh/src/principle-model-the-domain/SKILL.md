# Model the Domain

把真实领域编码进一个数据结构，而不是把它散落在条件语句里。一个与领域匹配的结构能让非法状态不可表示，并删掉分支。在写代码时选定它很便宜；之后再找回它就看起来像一次重构，于是被推迟。

优先考虑：

- 用状态机代替散落的布尔值、阶段标志或生命周期检查。
- 用类型化模型代替松散参数或重复的形状假设。
- 用 map、注册表、查找表或判别联合（discriminated union）代替散布在多个文件里的分支。
- 用 reducer 或命令/事件模型代替临时的状态修改。
- 用围绕某一块领域知识组织的模块，代替加载、校验、转换、保存这类顺序式划分。执行顺序不是所有权。
- 用一个小模块边界收拢重复出现的行为、所有权或不变量。
- 在访问模式需要的地方，用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。如果没有合适的，就先想清楚代码绝不允许什么、数据如何被读取，然后找到恰好编码了这些的结构。

不要强加抽象。如果当前的形状已经清晰、局部化、而且不太可能增长，宁可平淡的代码。对一个增加了间接层却没有减少分支、重复规则、非法状态或生命周期风险的抽象，保持怀疑。

跳过这一步的信号是：一个新功能让已有的 if/else 链又长了一支，或者出现第二个必须与第一个保持同步的布尔值。时间性分解是另一个信号：以阶段命名的模块在各个步骤里重复同样的领域规则。
