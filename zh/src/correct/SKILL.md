# Correct

操作者在不断纠正这个仓库里的代理犯同样的错误。改变仓库，让下一个代理犯不了。

假设每个贡献者都是一个只看它打开过的文件的代理，抄最近的示例，走能编译的最短路径。把仓库设计成：从一个文件内部看是对的改动，对整个仓库也是对的。

## 找出错误类别

先读最近的提交、回滚、审查评论、代理指令文件、以及解释变通方案的注释。把错误归类。一类错误出现两次才算成立。

## 在能生效的最高层级修每一类

1. **用架构消灭它。** 给每份状态一个 owner，给每项任务一条受支持的方式。藏起内部实现，让错误的 import 直接失败。用手同步的列表换成单一事实来源。删掉代理会去抄的旧方式和死代码。
2. **用类型强制它，让坏状态写不出来。** 如果坏代码仍能编译，加一个 lint 或 CI 检查，其报错信息写明应改用的文件、类型或函数。如果该模式已经很普遍，只在改动新增更多时才失败。
3. **测试那个行为。** 修掉或删掉任何在它检查的行为坏掉时仍通过、或只在内部实现变化时就失败的测试。
4. **文档或代理规则放最后，只写给需要判断的场合。** 代理跳过它们时不会有任何东西失败。

## 修复并证明

然后立刻修最高频的类别，每类一个提交。证明每道新检查在真实的过往错误上会失败。同一条命令在本地和 CI 都跑。例外写在违规的那一行上，带理由、过期日期和一个人类的批准。

## 保留规则表

最后，在代理指令文件里维护一张表，把每条规则与强制它的机制配对。操作者纠正你时，修掉错误并补上规则。如果规则已经在那里却没有任何东西强制它，那是一次重犯，所以在同一个改动里把它修到最高层级。错误不再可能发生时，删掉那条规则。

**回复：** 每一类错误及其证据、你选的层级、以及为什么更高的层级行不通。
