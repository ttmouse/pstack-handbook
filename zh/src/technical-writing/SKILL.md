# Technical writing

让疲惫的工程师一遍读懂。

- 砍掉每个不起作用的词。
- 用短的日常词："use"，不是"utilize"。
- 当一条规则把句子变得更糟，用别的方式修句子，或者不动它。
- 写真实的符号、文件、flag 或命令名，不要写同义词或对它的描述。
- 不发明行话。用开发者口头会说的词。命名模式第一次出现时说清它的含义。

## 变换节奏

- 混合句子长度。承载两个想法的句子拆开。只承载一个想法的长句保留。
- 解释性内容要有视角。参考性内容保持干。
- 具体一点。不写"schema 变更可能导致问题"，写"列重命名会让构建失败"。

## 先选模式（Diátaxis）

一份文档，一种模式。不要混模式。宁可拆开再互链。

- **Tutorial：边做边学。** 说清学习者会做出什么。每一步都产出可见的结果，并说明他应该看到什么。解释只给一个从句加一个链接。
- **How-to：通向目标的步骤。** 解决读者的问题。假设读者有能力。只写操作。允许分叉。按任务给指南命名。
- **Reference：供查阅的事实。** 只做描述。干、完整、确定。镜像被描述对象的结构。
- **Explanation：理解和原因。** 一个有边界的主题。给出背景：设计决策、历史、约束、备选方案。观点只允许出现在这里。

## 对着读者写句子（Google 开发者文风）

- 用"你"对读者说话，用现在时。
- 说清谁做什么。只有施动者未知或不重要时才用被动。
- 指令写成命令。条件放在指令前，常见情况放前面。
- 不用流行词，不用比喻，不写"请"，操作步骤里永远不写"simply"、"easy"、"quickly"。
- 不预先预告，连续的句子不用同一个短语开头。
- 链接文字要说明链接指向哪里。
- 标题承载要点，用 sentence case。每页一个 h1，不跳级。
- 序列用编号列表，其余用圆点列表。列表前用一个完整的句子引入。列表项保持结构一致。
- 代码用代码字体。UI 元素加粗。使用串行逗号。去掉"etc."。

## 让每条陈述一次只承载一层（STE 规则）

- 每句一条指令。其他地方每句一个想法。
- 超过约 20 词的指令、超过约 25 词的其他句子拆开。
- 警告或条件放在它所保护的那一步之前。
- 保留"the"和"a"。
- 每个词只有一个含义，每个动作用一个词。
- 操作步骤写成直接命令，绝不写成叙述，也绝不用被动。
- 能避则避免"-ing"形式的词。

## 不给任何句子留下两种读法（Global English）

- "only"、"not" 这类词紧贴它们修饰的词。
- 拆开长名词串。
- 每个"it"、"they"、"this"都指向一个明显的东西。绝不用"this"或"which"指代整个从句。
- 不省略动词，也不省略显示结构的小词，比如"that"。
- 一组并列项里重复冠词，避免误读。说清"and"或"or"连接的是哪些部分。
- 用句号，不用分号或破折号。不用斜杠，不用"(s)"。括号里的内容是完整的语法单元。
- 每个东西只用一个名字，处处一致。
- 不用习语、俚语、拉丁缩写和比喻。

## 文风与仓库细则

- 本技能碰到的每份文档都应用 **unslop** 技能。AI 词汇表、填充语、含糊限定词、格式化痕迹的目录归它管。
- PR 描述和 commit message 也是写作。除 Diátaxis 外每一层都适用于它们。PR 正文是一份评审者一分钟能读完的简报。不要粘贴 swarm 日志、SHA 列表或指标表格，给链接。
- 产品 UI 文案不算文档。那些走你们产品的文案规范。
- 代码片段用 tab 缩进。写真实路径。每个计数或目录结构的声明要在落地的那个 commit 上为真，并附上重新生成它的命令。
