# TDD Bug 修复

修一个有清晰、廉价测试路径的 bug 时，先让坏行为变成可执行的测试，再改生产代码。目标是写一个聚焦的回归测试：修复前失败，修复后通过。

当测试不现实时不要硬写。如果可用的测试需要大范围 harness 搭建、脆弱的 mock、缓慢的端到端基础设施、只能在生产环境造出的状态、模糊的复现步骤，或者会牵动大量无关 fixture，就不新增测试，改用最接近的有效验证方式。

## 工作流

1. **理解 bug。** 弄清预期行为、当前行为、受影响的路径、最小的可观察复现。
2. **选最窄的可执行检查。** 优先用这条代码路径已有的、最接近的单元测试、组件测试、集成测试或回归测试。如果没有现实可行的测试路径，不要为了走完流程从零硬造一个。
3. **先写失败测试。** 加一个能抓住这个 bug 的最小聚焦测试。测试应编码预期行为，而不是复刻当前实现。
4. **修复前先跑新测试。** 确认它因预期的原因失败。引用失败的具体内容，而不是断言行：异常、对字面量查出空结果、预测的不匹配都会打红，只有最后一种证明测试真的测到了这个 bug。如果它通过，或因无关原因失败，先修正测试或复现方式，再动实现。
5. **修 bug。** 做最小的生产代码改动，满足预期行为，同时保住周边契约。
6. **重跑回归测试。** 确认测试现在通过。

## 当失败测试不现实时

改用最接近的可执行回归检查：一个针对性的脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可没有新测试，也不要一个坏测试。坏测试是这样的：大部分在测 mock、编码了当前实现细节、依赖时序或无关的全局状态、为一个小修需要昂贵的基础设施，或者在证明修复之后就该立刻删掉。

## 护栏

- 不要为了让测试匹配一个错误实现而改测试。
- 除非预期行为真的变了且理由清楚，否则不要削弱已有断言。
- 回归测试聚焦在 bug 上。避免大范围 fixture 改动或无关的覆盖扩张。
- 如果 bug 本身是偶发的，尽量把测试做成确定性的，并写清锁住的是什么信号。
- 如果 bug 暴露了更大一类的失败，先落地聚焦的回归路径，再考虑给同类问题补覆盖。

## 最终回复

报告证据，不只是结论：

- 指出修复前失败的测试或可执行检查，并引用它产生的失败内容，裁剪到只留差异部分。
- 指出修复后通过的测试运行，以及做过的任何周边验证。
- 如果无法给出修复前的失败证据，说明原因，并描述改用了哪个最接近的回归检查。
