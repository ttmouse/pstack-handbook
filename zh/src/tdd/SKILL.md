# TDD Bug Fix

修复一个有清晰、廉价测试路径的 bug 时，在改动生产代码之前，把坏掉的行为变成可执行的。目标是拿到一个聚焦的回归测试：修复前失败，修复后通过。

测试不现实时不要硬造。如果可用的测试需要大范围的宿主（harness）搭建、脆弱的 mock、缓慢的端到端基础设施、只存在于生产环境的状态、模糊的复现步骤、或大量无关的 fixture 改动，就不要加新测试，改用最接近的有用验证。

## 工作流

1. **理解 bug。** 找出预期行为、当前行为、受影响路径、最小的可观察复现。
2. **选最窄的可执行检查。** 优先使用该代码路径已有的最近的单元、组件、集成或回归测试。没有明显可行的测试路径时，不要为了满足流程而从零造一个。
3. **先写失败的测试。** 添加能抓住这个 bug 的最小聚焦测试。测试应编码预期行为，而不是镜像当前实现。
4. **修复前运行新测试。** 确认它因预期的原因失败。引用失败的内容，不是断言那一行：一个异常、对字面值得到空结果、以及预测的不匹配都会打印红色，只有最后一种证明测试度量了这个 bug。如果它通过、或因无关原因失败，先修正测试或复现，再动实现。
5. **修 bug。** 做满足预期行为的最小生产改动，同时保住周边契约。
6. **重跑回归测试。** 确认测试现在通过。

## 失败测试不现实时

改用最接近的可执行回归检查：一个有针对性的脚本、手动复现命令、浏览器自动化、快照对比、日志断言、或聚焦的集成检查。

宁可没有新测试，也不要坏测试。坏测试是：主要在测 mock、编码了当前实现细节、依赖时序或无关的全局状态、为一个小修复需要昂贵的基础设施、或在证明修复后就会被立刻删掉的测试。

## 护栏

- 不要为了迁就错误实现而改测试。
- 不要削弱已有断言，除非预期行为真的变了且原因清楚。
- 让回归测试聚焦在这个 bug 上。避免大范围的 fixture 改动或无关的覆盖扩张。
- bug 是 flaky 的，尽可能把测试做成确定性的，并记录被锁定的信号。
- bug 暴露了更大一类失败时，先落地聚焦的回归路径，再考虑额外的同类覆盖。

## 最终回复

报告证据，不只是结果：

- 点名失败在先的测试或可执行检查，引用它产生的失败，裁剪到 diff。
- 点名通过在后的测试运行，以及做过的任何周边验证。
- 无法演示失败在先的证据时，说明原因，并描述改用的最接近的回归检查。
