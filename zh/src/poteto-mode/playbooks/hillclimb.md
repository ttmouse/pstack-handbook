### Hillclimb

**指标和实验的完整性归你。监督、评审。尝试委托出去。** 用于对单一可度量事物做持续的迭代改进、逼近目标。一次性修复是 Bug fix 或 Perf issue；这里是循环。

核心纪律：一次改动、一次测量、保留或回滚。绝不堆叠未验证的改动，也绝不靠读代码宣布胜利（**prove-it-works** 原则技能）。

1. 选指标之前先落定工作负载和架构。追溯目标，列出可能移动结果的真实工作负载维度（数据量、历史、状态、并发），选一个能复现用户抱怨的用例。没有用例能复现，就先修 repro，别急着爬坡。然后定死三样东西：唯一的指标、「更好」的方向、以及一条可检查的停止谓词——谓词要把目标值和尝试次数下限配对，防止早期走运的一次胜利提前结束整场（示例「比基线好至少 50% 且至少 10 轮迭代」就是这种形状）。用户给了数字就用用户的，否则先商定。
2. 搭测量台架，证明它有区分度，然后冻结（**build-the-lever** 原则技能）。跑对比鲜明的真实工作负载，确认目标用例复现症状、且更容易的用例按预期区分开。台架分不开就改工作负载或指标。冻结前用 **benchmark-checklist** 技能审查台架，并让它打印错误数和工作量计数。冻结后，一条可重复的命令输出指标，采样足够多以盖过噪音（N 次取中位数，不是单次跑）。任何改动之前，记录基线指标和回归闸门（必须保持通过的测试）的绿跑。
3. 用 **show-me-your-work** 技能开决策日志。一个 `decision.tsv`，每次尝试一行：id、假设、改动、before、after、delta、tests、裁决（kept 或 reverted）、备注。每次尝试前先读它。放在树外（gitignore）。
4. 每个假设都要落在步骤 1 的架构模型上，点名具体机制（「把 X 挪出启动路径，因为它阻塞首屏」），而不是「试试某处加个 memoization」。性能指标的话，按 Perf issue playbook（`playbooks/perf-issue.md`）步骤 2 的性能箴言排序假设。只借它们的顺序，不借那一步的停止规则。
5. 循环，每轮一个假设：
   - 把改动交给子代理，使用你配置的 hillclimb 模型（默认见 poteto-mode 的 Models 一节），范围收紧。按 poteto-mode 的 Subagents 一节为每个子代理选合适的推理档位。监督并评审 diff，而不是自己敲（**guard-the-context-window** 原则技能）。多个独立假设同时活着时，扇给并行子代理，各自在自己的工作树里（**separate-before-serializing-shared-state** 原则技能）。
   - 用冻结的台架测 before 和 after，并跑回归闸门。
   - 只有指标越过噪音、且闸门保持绿才接受。否则完整回滚改动。「也许有用」的小调整不保留。
   - 每个被接受的修复一个提交，只 stage 你改过的文件（`git add <files>`，绝不用 `-A`）。无论保留还是回滚，都记一行日志。
   每轮迭代以一次检查收尾，下一轮才开始（**sequence-verifiable-units** 原则技能）。无人值守运行时，只从 Autonomous run playbook（`playbooks/autonomous-run.md`）借唤醒机制，不借它的停止规则。
6. 翻过第一个平台期。停滞不前、连续多个被拒时：换问题类别、合并几个擦边方案、重读源码、或试一个更激进的打法，再下结论说山头已被登顶。正确性和简单性优先于数字。回滚一个破坏行为的胜利，保留一个守住了数字的简化（**laziness-protocol** 原则技能）。
7. 谓词达成，或剩下的想法边际收益不值得成本时停。不为达标而放宽谓词，也不在还有便宜未试假设时退出。卡住了就上报，不要空转。
8. 走 **Opening a PR** 流程，被接受的提交按落地的先后 stack。

**汇报：** 指标和目标、基线到终值及百分比 delta、迭代轮数（保留 vs 回滚）、每个被接受修复一行、`decision.tsv` 路径、以及如果继续推下一个最值得试的想法。
