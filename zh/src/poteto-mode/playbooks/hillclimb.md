### Hillclimb

**你拥有指标和实验的完整性。监督并 review。委托尝试。** 用于针对一个目标，对单个可度量事物做持续的迭代改进。一次性的修复走 Bug fix 或 Perf issue。这是循环。

核心纪律：一次改动，一次测量，保留或回滚。绝不堆叠未测试的改动，绝不靠看代码就宣称赢了（**prove-it-works** 原则 skill）。

1. 在选择指标之前，先摸清 workload 和架构。对目标跑 **how** skill，点名能推动结果的现实 workload 维度（数据量、历史、状态、并发），并选出一个能复现用户抱怨的用例。没有用例能复现它，就先修 repro，而不是爬山。然后固定一个指标、算作更好的方向、以及一个可检查的停止谓词，谓词要把目标与尝试次数下限配对，防止一次幸运的早期获胜提前终结运行（"至少比基线好 50% 且至少 10 轮迭代"这个示例就是这个形状）。用户给了数字就用用户的，否则商定。
2. 搭建测量宿主，证明它的灵敏度，然后冻结它（**build-the-lever** 原则 skill）。运行对比性的真实 workload，确认目标用例复现症状、而更容易的用例按预期区分开来。如果宿主分不开它们，修改 workload 或指标。冻结之前用 **benchmark-checklist** skill 审查宿主，并让它打印自己的错误计数和工作量计数。冻结之后，一条可重复的命令发出指标，采样要足以压过噪声（N 次的中位数，不是单次运行）。在任何改动之前，记录基线指标和回归闸门（那些必须持续通过的测试）的一次绿色运行。
3. 通过 **show-me-your-work** skill 开启决策日志。一个 `decision.tsv`，每次尝试一行：id、假设、改动、before、after、delta、tests、verdict（保留或回滚）、note。每次尝试之前读它。把它放在代码树之外（gitignore 掉）。
4. 让每个假设都扎根于第 1 步的架构模型，使它指名一个具体的机制（"把 X 从 boot 路径上挪走，因为它阻塞首屏"），而不是"试着 memoize 一下什么"。对性能指标，按 Perf issue playbook（`playbooks/perf-issue.md`）第 2 步的性能口诀排列假设的顺序。只借用它们的顺序，不借那一步的停止规则。
5. 循环，每轮迭代一个假设：
   - 用你配置的 hillclimb 模型（默认值在 poteto-mode 的 Models 一节）把改动交给一个子代理，范围收紧。按 Subagents 一节为每个子代理挑选与任务匹配的推理档位。监督并 review diff，而不是自己敲（**guard-the-context-window** 原则 skill）。当多个互相独立的假设同时活跃时，扇出给并行的子代理，每个在各自的工作树里（**separate-before-serializing-shared-state** 原则 skill）。
   - 用冻结的宿主测 before 和 after，并跑回归闸门。
   - 只有指标移动幅度超过噪声、且闸门保持绿色时才接受。否则把改动完整回滚。"可能有帮助"的小调整不保留。
   - 每个被接受的修复一次提交，只 stage 你改的文件（`git add <files>`，绝不用 `-A`）。无论保留还是回滚，那一行都要记。
   每轮迭代在下轮开始之前以一次检查收尾（**sequence-verifiable-units** 原则 skill）。如果运行无人值守，只从 Autonomous run playbook（`playbooks/autonomous-run.md`）借唤醒机制，不借它的停止规则。
6. 推过第一个平台期。停滞时——连续多次被拒——换一个类别、合并那些差一点的方案、重读源码、或在断言这座山已被登顶之前试更激进的东西。正确性和简单性排在数字前面。回滚一个破坏行为的胜利，保留一个守住数字的简化（**laziness-protocol** 原则 skill）。
7. 谓词满足时停止，或当剩余的想法都是边缘性的、不值得其成本时停止。不要放宽谓词来够到它，也不要在还有廉价未试假设时退出。卡住了就上报，不要空转。
8. 把被接受的提交按落地顺序堆叠起来，运行 **Opening a PR**。

**回复：** 指标与目标、从基线到最终值及百分比 delta、跑了几轮迭代（保留对回滚）、每个被接受的修复占一行、`decision.tsv` 路径，以及如果继续推进你最想试的下一个想法。
