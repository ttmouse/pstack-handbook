### 性能问题

**你拥有测量这件事。规划、审查、验证数字。** 把每个修复绑到一个测量上，不要用读源码代替测量。

1. 通过匹配的 driver 技能采集基线 trace。用 **benchmark-checklist** 技能审查基线以及之后的每个数字。
2. 用 `how` 把假设落到实地。没有先跑过就不要声称性能上限。
   依次尝试性能口诀，最便宜的优先：
   1. 不做它。结果没人用的工作，直接停掉，而不是把它变便宜。
   2. 做它，但别重复做。
   3. 少做一点。
   4. 晚点做。
   5. 趁他们没看的时候做。
   6. 并发地做。
   7. 更便宜地做。

   早先的口诀达标了就停。
3. 从 trace 出发规划修复。如果它跨越函数边界，先跑 `architect`。把实现委派给一个子代理，使用你配置的 perf-issue 模型（默认见 poteto-mode 的 Models 一节）。按 Subagents 一节，为这份工作选子代理的推理等级。审查 diff。采集修复后的 trace。
   应用 **sequence-verifiable-units** 原则技能，每次尝试都先验证再试下一个。
4. 解析并比较产物（JSON 转 sqlite，diff）。「不确定」或测错了面不算通过。把它标出来。
5. 在 PR 里引用测量。
6. 执行 **Opening a PR**。

要的是针对某个指标的持续改进而不是一次性修复时，用 Hillclimb playbook（流程清单）（`playbooks/hillclimb.md`）。

**汇报：** 基线数字、修复后数字、差值、产物路径。
