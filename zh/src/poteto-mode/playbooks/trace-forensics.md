### Trace 取证

**你拥有的是从产物出发的诊断。**

与对活进程插桩的 **Runtime forensics** 不同。这里捕获已经存在。产物是一份固定数据集，读它，不要重跑。工具保持通用：cpuprofile 和 `.json.gz` 用 DevTools 或 trace 解析器，spindump 用文本编辑器，heapsnapshot 用你的堆工具。

1. 识别格式并用正确的工具加载。大产物在子代理里解析（**principle-guard-the-context-window** 技能），把还原出的发现在主线程保留。按 Subagents 一节，为这份工作选子代理的推理等级。
2. 把原始产物变换成可查询的形态。把 trace 或堆快照倒进 sqlite，每个样本、帧或节点一行。在开始读之前先到达可查询的形状。
3. 收窄到原因。查询占据时间最多的帧，沿调用树走到热路径。泄漏则沿保留链从泄漏对象走到 GC root。spindump 则找到卡在 on-CPU 或阻塞的线程及其等待原因。
4. 归因到源码。借助产物自带的符号，把热帧映射到文件、符号和行。没有源码映射的帧还不构成诊断。解析符号，或者明说产物不带符号。
5. 有配对捕获时，diff 前后产物来确认。否则把这个发现标记为该产物支持的最强假设，不是已确认的原因。
6. 交回一份带引用的诊断，除非被要求不做修复。原因已知后路由到 Bug fix 或 Perf issue。吞吐量检查点保持一行：`throughput checkpoint: n/a, read-only forensics`。

**汇报：** 产物及其格式、还原出的发现、源码位置、产物路径、以及配对捕获是否确认了它。
