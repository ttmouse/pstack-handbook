### Orchestrate

通过 [poteto-mode 的 Non-negotiables](../SKILL.md#non-negotiables) 解析 driver 技能。

**你运行的是程序，不是代码。决定哪份工作交给哪个代理去完成，然后检查每个代理产出了什么。** 适用于交给一个协调者会话的常驻项目：跨多天、多个堆叠 PR、几十到几百个子代理、极少的人类轮次。单个任务驱动到谓词条件为止，那是 Autonomous run。一次雄心勃勃、需要定制工作流的运行，是 figure-it-out。一个代理在会话预算内就能完成的工作，不是程序。

用自己的工具来运行它。用 `Agent` 生成 worker。把程序状态保存在 `~/.claude/orchestrate/<slug>/` 下的一个存储里，放在仓库之外，以 `notes.md` 作为追踪器。当宿主支持时，用 PR 和 CI 事件订阅来监视每个 PR。不调用任何脚本，不跑任何轮询循环，也绝不在代理之间转发消息或状态。

#### 拓扑

- **每个 PR 一个 owner。** owner 是其分支唯一的写入者，把这个 PR 从构建一路带到合并。只有 owner 才能 push、rebase 或改目标。关闭或改一个基础 PR 的目标会让它上面的每个 PR 变成孤儿，所以 owner 只有在你下令时才这么做。你绝不编写或修改代码。冲突的合并、链式 rebase 和修复都交给 owner。
- **每个独立任务一个全新 worker。** 它的 kickoff 携带它所需的一切，包括它依赖的每份上游报告，全文粘贴进去。worker 看不见自己的兄弟。以后台子代理（`run_in_background: true`）的方式运行 worker。Claude Code 没有远程 worker 环境，所以给每个写入者自己的工作树或分支，并通过 driver 技能跑运行时检查。按 Subagents 一节，为每份工作选子代理的推理等级。
- **只有一个区域有多个并行 worker 时才设子协调者。** 它拥有那个区域的 worker 和 kickoff，只给你发一份汇总，绝不发原始 worker 报告。最多三层就停：你、子协调者、worker。每个协调者保持在飞约十个 worker，一个完成就启动下一个，而不是等整批。
- **当新工作需要某个 worker 已构建的状态时**，比如它的 checkout 或未提交的改动，在该 worker 的工作树里启动一个全新 worker。Claude Code 的 fork 复制的是协调者，不是 worker。给某个 worker 发消息只限于同一工作的后续跟进。绝不发消息去查岗，因为一条消息会重启一个空闲代理。
- **每个 PR 拿到一个不是它作者的验证者**，用不同的模型家族。owner 只在该验证者在当前 head 上通过时才合并。
- **从单个单元开始。** 先把它走完 kickoff、owner、验证者和合并的全程再扇出，这样 kickoff 的缺陷只会付出一个代理的代价，而不是五十个。在几乎相同且廉价的单元上，第一个单元就是那次测试。

#### 监督

- **每份 kickoff 都要指名能证明工作完成的证据**，比如一条命令及其预期输出、一次 driver 技能检查，或一个产物。它还要指名目标、worker 可以写和不可以写的路径，以及它绝不能采取的行动。如果你说不出证据，这个单元还没圈定好范围。
- **读 diff 或产物，而不只是 worker 的总结。** CI 绿色是裁决的一个输入，不是裁决。行为性的工作需要的不止一次类型检查。一份裁决只覆盖一个 head SHA，所以新的 push 需要新的裁决。在每个子协调者的 worker 运行期间抽查它的 kickoff，有一份失败就修它的指令。
- **把偏离范围或超出所求的工作退回去。** 只保留阻塞程序本身的修复，其余的存为后续任务。
- **在汇报一个 PR 之前先检查它的实时状态**，用 `gh pr view` 和 `gh pr checks` 或你的 forge 的等价命令，而不是 worker 的最后一份报告。把你生成的每个 worker 记账为：完成、被替换，或被并入另一个 worker 的范围。
- **停止或替换一个停滞或打转的 worker。** 用它的 push 和 PR 活动来评判，而不是它的状态文本。按原因重试：上下文或内存超限后缩小范围，连接断开后用同一份 kickoff，工具报错后换一个模型。重试两次之后，丢弃该单元并围绕它重新规划。当一个已停止的 worker 迟到返回时，对照 PR 的当前状态检查它的结果，把任何独有的发现交给一个新 worker。
- **只向用户请求真正的决策或真正的阻塞**，比如不可逆的操作、实验无法裁决的产品或偏好判断，或一次重新规划之后依然存在的死路。rebase 机制、重试、CI 抖动、评审分诊和「我该继续吗」永远不要送到用户那里。

**汇报：** 针对目标落了什么、每个 PR 的实时状态与裁决及其链接、丢弃了什么以及为什么、以及等用户决策的事项。
