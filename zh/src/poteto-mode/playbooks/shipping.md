### Shipping

通过 [poteto-mode 的 Non-negotiables](../SKILL.md#non-negotiables) 解析 driver skill。

**落地归你。每个 PR 独立验证，只从根落地那条已验证的链，然后撒手不管 stack。** 落地需要用户的落地权限，且每次落地在下一次开始前得到确认。

1. **解析 forge，然后在落地之前逐个独立验证每个 PR。** GitHub CLI（`gh`）是默认。如果 `command -v origin` 成功且 Origin 能解析该仓库，所有 PR 操作走 `origin pr`。否则留在 `gh` 并记录这个回退。绝不要求 Graphite（`gt`）。自底向上捕获受影响的链：每个 head 分支和 SHA、base 分支和 SHA、以及目标仓库和分支，不碰无关的 PR。在合并、布防、rebase、改 base 之前先读 [Merge and restack safety](../references/merge-safety.md)。进场时检查待处理的 merge request，凡缺少步骤 4 验证闸门的，先取消并读回，再等长评审。每个 PR 一个验证器，各为自己工作树里的子代理，像用户一样通过 driver skill 跑这次改动、以 head 为对照，在该 PR 上贴 `PASS`、`PASS+NOTES` 或 `FAIL`。只有来自没写过这份代码的代理的裁决才算数，因为作者检查的是它想建的东西。绿 CI 和机器人的批准评审都不是裁决，因为两者都没有像用户那样运行这次改动。记录每份裁决的 head SHA、base SHA、base 分支、以及 base-to-head diff 的稳定 `git patch-id`。
2. **只落地从底部 rooted 的连续已验证段。** 从最低的未合并 PR 向上走，遇到第一个没有 `PASS` 或 `PASS+NOTES` 的就停。它下面的那些 PR 就是本次运行，最上面那个是天花板。已验证的 PR 在某个未验证 PR 之上时要等待，因为下面的代码不落地它就无法落地。一个分支既不持有也不需要那段代码的 PR，可以改挂到 trunk 并独自落地——但它需要一份新裁决，因为旧裁决是在那段代码垫在下面时跑出来的，而 trunk 没有那段代码。
3. **复核裁决是否仍然描述这份代码。** 裁决覆盖一个补丁，而链上一次 rebase 会把它上面每个 PR 都移到新 SHA，且不让任何检查失败。信任一份旧裁决之前，先比较裁决 SHA 处的 `git patch-id` 与当前 head。当补丁只在测试、文档或 lint 配置上有差异时，一条 lane 的结果仍然成立——只要它当时跑的构建在这两个 SHA 处除噪音外相同。噪音指在裁决 SHA 的两次构建之间也会出现的差异，或内嵌的提交 SHA。每类噪音都要报告涉及的文件，让读者能核查这个判断。改动本身仍然要拿新检查和新评审，因为旧裁决从没见过它。没有构建输出的 lane（比如 dev server）无法做这种证明，所以要重跑；其他任何漂移的东西也要重新验证。patch-id 相同才能保住一份评审——且前提是你确认它适用于新的目标分支和依赖——所以行为有变化或适用性不确定时重新验证，每次 rewrite 或 retarget 之后重跑检查和可合并性。
4. **自底向上，一次落地一个 PR。** 永远在服务端强制的 head 条件下合并运行中最低的未合并 PR，因为没有这个条件的最后时刻读取会留下竞态。GitHub 上用 `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head>`，并在发请求前确认目标分支正确，因为 head 守卫不守卫 base。只有当 Origin 的 CLI 能证明等价的服务端 head 条件时才用 `origin pr merge <pr>`；否则停在 merge-ready 并报告这个限制。在 Origin 上，普通命令还会把低于你所指 PR 的所有 PR 一起合并；在 GitHub 上，base 仍是父分支的 PR 会合进父分支而不是 trunk。读回 PR 确认结果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因为合并命令可能在合并队列只是排了队时也报成功，而请求中的 auto-merge 不是合并。已落地的 PR 显示 merged 且 base 是 trunk，而不是它的父分支。然后 fetch 目标分支并确认合并提交进了它的历史；任何与已验证落地相矛盾的地方都让整条链停下。`--auto`（Origin 的 merge-when-ready 或 GitHub 的 auto-merge）只布防在裁决覆盖其当前 head 的 PR 上——因为它落地的是任何就绪的 head——且只在强制该裁决和必需 CI 于将要落地那个 revision 的仓库规则之后。队列强制的分支会把普通合并变成队列准入，所以同样要那些规则。绝不为达目的修改保护设置或使用 `--admin`。任何 push、rebase 或 base 编辑之前，对该改动可能影响的每个 PR 跑安全参考里的 `ship-pr inspect` 和 `ship-pr cancel-pending`，并要求得到 `cancelled` 结果。取消失败、状态不可用、或期间有 PR 合并了，就停下来先对齐真实状态。一次合并落地后，把 base 原是那条被合并分支的 PR 改挂到 trunk（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），从记录下来的旧父边界只把它自己的提交重放到合并结果上（如安全参考所述），并带上改写前捕获的远端 SHA 的 lease push。裁决覆盖的是补丁而不是提交，所以裁决是否幸存由步骤 3 的 patch-id 规则决定。它的检查通过且裁决幸存后就合并。
5. **stack 落地期间不要碰它。** 步骤 4 对下一个 PR 的改挂是对分支或 base 的唯一改动，因为一次合并落下的就是它的分支和 base 在那一刻持有的东西，无论有没有裁决。GitHub 上，用已安装插件下的 `skills/poteto-mode/scripts/watch-pr/watch-pr --queued-stack`、在动态模式的 `/loop` 下盯着这次运行，直到它在天花板处报 `COMPLETE`。把运行的 PR 号自底向上传进 `--stack-prs`，每次重启 watcher 都传同一份列表。Origin 上，每次 `origin pr checks <pr> --watch` 返回后用 `origin pr view <pr> --checks` 重读当前 PR，直到天花板显示 merged。父分支合并后 base 移到 trunk 是预期行为，不是需要修复的损伤。合并停滞时，先弄清原因再改任何东西。每次唤醒，用 `ship-pr inspect` 把落地 revision（含 base OID）与已批准的记录比对，取消证据已不再适用的待处理请求。

   Watcher 负责 GitHub 的 blocker 分类。保留 `BLOCKER` 原因并按 `playbooks/babysit.md` 路由：冲突和 `behind-base` 给拓扑 owner，评审线程和 CI 给 PR owner，人工审批闸门归入等待。不要给未变化的 blocker 重新布防。`WAITING`（含 `merge-queue`）是非终态。待处理的检查既不是失败也不是完成。`TIMEOUT` 和 `status-query` blocker 要做诊断，因为状态不明永远不允许合并。
6. **到天花板就停。** 扩大运行需要新裁决，所以那是重新走一遍步骤 1。

**汇报：** 已验证的运行及其天花板、每个 PR 的裁决及其出处、布防或取消了什么并读回了什么、什么落地了以及怎么确认的、任何未解决的状态或服务限制、以及下一个缺口需要什么。
