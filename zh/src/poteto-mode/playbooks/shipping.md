### 交付

通过 [poteto-mode 的 Non-negotiables](../SKILL.md#non-negotiables) 解析 driver 技能。

**你拥有的是落地。独立验证每个 PR，只从根部落下已验证的运行段，然后撒手不管这个栈。** 落地需要用户的落地权限，且每次落地确认之后才开始下一次。

1. **先解析 forge，然后在每个 PR 落地前独立验证它。** GitHub CLI（`gh`）是默认。如果 `command -v origin` 成功且 Origin 能解析该仓库，则所有 PR 操作都用 `origin pr`。否则留在 `gh` 上并记录这次回退。绝不要求 Graphite（`gt`）。自底向上捕获受影响的链：每个 head 分支和 SHA、每个 base 分支和 SHA、预期的目标仓库和分支，不碰无关的 PR。在合并、布防、rebase 或改目标之前读 [Merge and restack safety](../references/merge-safety.md)。进入时检查待处理的 merge 请求，凡缺少第 4 步验证闸门的，在冗长评审之前取消并回读。每个 PR 一个验证者，各自是独立工作树中的子代理，像用户那样通过 driver 技能跑这个改动，parent 对 head，并在该 PR 上发布 `PASS`、`PASS+NOTES` 或 `FAIL`。只有没写过这段代码的代理给出的裁决才算数，因为作者检查的是它想建的东西。CI 绿色和机器人评审通过不是裁决，因为它们都不像用户那样运行这个改动。记录每个裁决的 head SHA、base SHA、base 分支，以及 base-to-head diff 的稳定 `git patch-id`。
2. **只落地以底部为根的连续已验证段。** 从最低的未合并 PR 向上走，遇到第一个没有 `PASS` 或 `PASS+NOTES` 的就停。它下面的 PR 构成这段运行，最顶上的那个是天花板。一个已验证的 PR 位于未验证的 PR 之上时要等待，因为离开它下面的代码它无法落地。一个分支既不依赖也不包含那段代码的 PR，可以移到 trunk 上独立落地。它需要一份新裁决，因为它那份旧的带着那段代码跑的，而 trunk 上没有那段代码。
3. **复查裁决是否仍然描述这段代码。** 一份裁决覆盖一个 patch，而一次链式 rebase 会把它上面每个 PR 移到新的 SHA 上，却不触发任何检查失败。信任较旧的裁决之前，比较裁决 SHA 处的 `git patch-id` 与当前 head。当 patch 只在测试、文档或 lint 配置上不同时，只要那条 lane 当时跑的东西在两个 SHA 上除噪声外构建相同，它的结果就仍然成立。噪声是那种在两次构建裁决 SHA 之间也会出现的差异，或内嵌的提交 SHA。每种噪声都带上它的文件来报告，让读者能核查这个判断。改动本身仍然要做全新检查和评审，因为旧裁决从没见过它。没有构建输出的 lane（比如 dev server）无法做这个判断，所以重跑它，其他任何漂移的东西也重新验证。patch-id 匹配时评审可以保留，前提是你检查过它适用于新的目标和依赖，所以行为变了或适用性不确定时重新验证，每次重写或改目标之后重跑检查和可合并性。
4. **自底向上落地，一次一个 PR。** 始终在有服务端强制的 head 条件下合并这段运行中最低的未合并 PR，因为不带条件的最后时刻读取会留下竞态。在 GitHub 上用 `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head>`，并在发请求前确认目标，因为 head 守卫不守 base。只有 Origin 的 CLI 证明了等价的服务端 head 条件后才用 `origin pr merge <pr>`。否则停在 merge-ready 并报告这个限制。在 Origin 上，普通命令还会把你所指 PR 之下的每个 PR 一起合并；在 GitHub 上，base 还是父分支的 PR 会合进那个父分支，而不是 trunk。回读 PR 看结果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因为合并命令可能报告成功而合并队列只是把它排了队，且被请求的 auto-merge 不是合并。已落地的 PR 应显示 merged 且 base 是 trunk，而不是它的父分支。然后 fetch 目标并确认合并提交已进入其历史，任何与已验证落地矛盾的地方都停止这条链。只对裁决覆盖其当前 head 的 PR 布防 `--auto`（Origin 的 merge-when-ready 或 GitHub 的 auto-merge），因为它落的是碰巧就绪的 head，且只能放在强制裁决和必需 CI 作用于将要落地那个版本上的仓库规则之后。要求走队列的分支会把一次普通合并变成队列准入，所以它需要同样的规则。绝不为此改保护设置，也绝不用 `--admin`。在每次 push、rebase 或 base 编辑之前，对这次改动可能影响的每个 PR 运行安全参考里的 `ship-pr inspect` 和 `ship-pr cancel-pending`，并要求返回 `cancelled` 结果。取消失败、状态不可用、或有 PR 在此期间合并了，就停下，先把实际状态核对清楚。一次合并落地后，把 base 原为那个已合并分支的 PR 改指向 trunk（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），从记录的旧父边界开始只把它的提交重放到合并结果上，如安全参考所述，并用重写之前捕获的远程 SHA 租约来 push。裁决覆盖的是 patch，不是它的提交，所以第 3 步的 patch-id 规则决定裁决是否仍然有效。它的检查通过且裁决存续后合并它。
5. **栈在落地期间不要碰。** 第 4 步对下一个 PR 的移动是对分支或 base 的唯一改动，因为一次合并落的是它的分支和 base 当时持有的全部内容，无论有没有裁决。在 GitHub 上，在 `/loop` 的 dynamic 模式下用 `playbooks/babysit.md` 的排队 watcher（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）监视这段运行，直到它在天花板处报告 `COMPLETE`。在 Origin 上，每次 `origin pr checks <pr> --watch` 返回时都用 `origin pr view <pr> --checks` 重读当前 PR，直到天花板显示 merged。base 在父分支合并时移到 trunk 是预期行为，不是要修复的损伤。合并停滞时先查明原因，再决定是否改动任何东西。每次唤醒时，通过 `ship-pr inspect` 把落地版本（含 base OID）与已批准的记录比较，取消证据已不再适用的待处理请求。

   watcher 负责 GitHub 阻塞分类。保留 `BLOCKER` 原因并按 `playbooks/babysit.md` 路由：冲突和 `behind-base` 交给拓扑 owner，线程和 CI 交给 PR owner，人工审批闸门转为等待。不要对未变化的阻塞重新布防。`WAITING`（包括 `merge-queue`）不是终态。待处理检查既不是失败也不是完成。诊断 `TIMEOUT` 和 `status-query` 阻塞，因为未知状态绝不允许合并。
6. **在天花板处停。** 扩展这段运行需要新的裁决，所以那是重新走一遍第 1 步。

**汇报：** 已验证的运行段及其天花板、每个 PR 的裁决及其产生者、布防或取消了什么、回读了什么、落了什么以及你如何确认、任何未解决的状态或服务限制、以及下一个空缺需要什么。
