### Bug fix

**这个任务归你。计划、评审、验证。** 调查和修复委托给子代理，主导权留在你手里。按 poteto-mode 的 Subagents 一节为每个子代理选合适的推理档位。

要科学。每一行发布的代码都能溯源到运行时证据。「也许有用」的双保险只是一个假设，不是修复——它不能发布。当证据推翻某个假设时，把它引发的那部分改动回滚。证据能支撑的最小改动才发布，多一行都不行。

在步骤 2–3 扇出之前，先看[聚焦修复例外](#聚焦修复例外)。打印诊断用的配置或服务响应之前，先选定已知的非敏感字段；不要整份倾倒配置或环境变量。

1. 自己在匹配的界面上用 driver skill（Non-negotiables）复现，即使调试或插桩协议说「请用户复现」也一样。只有在给出明确、具体的原因说明控制界面够不到目标时才请用户，而且要先把界面驱动到极限。直接复现不出来，就合成触发条件、收紧条件、或加插桩，直到它触发。
2. 二分定位原因。列出候选假设，逐个排除，直到剩下一个。用受影响子系统的 trace 和 **why** 技能（回归历史）来播种假设。每一轮都取能切掉最多剩余问题空间的那个分叉，取运行时证据，排除。程序状态不清楚时，加插桩或日志，在代码运行时读它。不要猜。漫长或顽固的追猎用 Claude Code 的 `loop` 技能驱动。在步骤 3 的 `architect` 或 `interrogate` 扇出之前，先用运行时证据确认幸存的那个*机制*。
3. 计划修复。如果跨越函数边界，先 `architect`。把实现委托给子代理，使用你配置的 bug-fix 模型（默认见 poteto-mode 的 Models 一节），并给一个具体范围。
4. 在同一个界面上验证。原来的 repro 现在通过。「不确定」或用错界面都不算通过，要标出来。单元测试展示的是分支行为，不是 bug 不存在。
5. 编排提交顺序，让失败的 repro 在 git 历史里先于修复落地。当这个 bug 有便宜的本地图测试路径时，参考 **tdd** 技能的「先写失败测试」节奏。测试太贵、太重集成、或不清晰时跳过。
   这是 **sequence-verifiable-units** 原则技能的范本：失败测试在底，修复在上。
6. 走 **Opening a PR** 流程。

任何 bug 修复，只要实现改动触及接口、所有权、schema、迁移行为、并发或事务保证、部署或路由契约——哪怕都在一个函数内——步骤 3 都要先跑 `architect` 再动手。标记 merge-ready 之前，凡涉及执行安全或数据完整性不变量的代码（包括原子资格守卫），即使修复本身保持了该不变量，也要求一名独立正确性评审。评审无法运行时，按 Subagents 的 closed-review-gate 规则处理。

**汇报：** 坏了什么、根因、修复、怎么验证的。引用决定性的失败与通过输出，裁剪到只剩断言和计数。

当发布或部署属于任务的一部分时，还要说明：修了什么代码并验证过、实际发布了什么、受影响的运行时实际在跑什么版本什么行为（必要时通过鉴权路径确认）、以及任何阻塞点和下一步需要的动作。运行时证据缺失或自相矛盾，事故就不算解决——即使发布已经成功。引用的证据要去掉凭据和客户数据。

#### 聚焦修复例外

在调用 `how` 或 `why` 之前，可以允许一个聚焦的 bug-fix 委托先用聚焦的代码和本地历史阅读来调查已复现的失败。只有以下条件全部成立，才可跳过这些技能和步骤 3 的 `architect`——即使跨越函数边界：

- 运行时证据已把原因锁定在一个子系统内。
- 修正保持接口和状态语义不变：没有签名、所有权、schema、迁移、安全、并发、事务、部署/路由方面的改动。安全改动包括认证、授权、密码学、密钥处理。
- 有一个便宜的回归检查能在相关运行时设置下触发该失败，且原始界面上的验证是可用的。
- 没有竞争的设计方案或相互矛盾的证据。

跳过之前，把支持这些条件的证据记进现有的 checklist。委托实现这个有范围边界的修复；主导者仍然负责计划、评审 diff、验证。任何一条不成立、或聚焦调查后仍存疑、或后续证据推翻了它，就回到步骤 2–3，不再走例外。其余所有步骤和任何要求的独立评审照旧有效。补丁大小本身永远不构成跳过的理由。
