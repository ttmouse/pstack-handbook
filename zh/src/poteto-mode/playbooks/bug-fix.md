### Bug fix

**你拥有这个任务。计划、review、验证。** 把调查和修复委托给子代理，你保持在主位。按 Subagents 一节为每个子代理挑选与任务匹配的推理档位。

保持科学态度。每一行被发布的代码都能追溯到运行时证据。"可能有帮助"的双保险是一个假设，不是修复。它不会被发布。当证据推翻一个假设时，回滚它引出的改动。证据能支撑的最小改动才发布，多一行都不行。

1. 通过 driver skill（Non-negotiables）在匹配的表面上亲自复现，即便某个 debug 或 instrumentation 协议说要让用户去复现。只有在给出了控制面无法触达目标的、明确而具体的理由时才问用户，而且要先把它驱动到极限之后。如果无法直接复现，就合成触发条件、收紧前提、或加 instrumentation，直到它触发。
2. 二分查找原因。列出候选假设，然后逐一排除，直到剩下一个。用 `how` 扫受影响的子系统、用 **why** skill 查回归历史来播种假设。每一轮，取能切掉最多剩余问题空间的那个分界，拿运行时证据，排除。当程序状态不明时，加 instrumentation 或日志并随代码运行去读它。不要猜。用 Claude Code 的 `loop` skill 驱动一场旷日持久的追猎。在第 3 步的 architect/interrogate 扇出之前，先用运行时证据确认幸存的那个*机制*。
3. 计划修复。如果它跨越函数边界，先跑 `architect`。用你配置的 bug-fix 模型（默认值在 poteto-mode 的 Models 一节）把实现委托给一个子代理，范围要具体。
4. 在同一个表面上验证。原始 repro 现在通过。"不确定"或表面不对不算通过。把它标出来。单元测试展示的是分支行为，不是 bug 的缺席。
5. 排布提交，让失败的 repro 在 git 历史里落在修复之前。当这个 bug 有廉价的本地测试路径时，看 **tdd** skill 的失败测试优先节奏。当测试会很贵、重度依赖集成、或路径不清时，跳过它。
   这是 **sequence-verifiable-units** 原则 skill 的典型范式：失败的测试在先，修复叠在上面。
6. 运行 **Opening a PR**。

**回复：** 什么坏了、根因、修复、你怎么验证的。引用决定性的失败与通过输出，裁剪到只剩断言和计数。
