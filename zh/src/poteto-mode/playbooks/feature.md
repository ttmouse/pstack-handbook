### Feature

**你拥有设计。计划、review、验证。** 委托实现。保持在主位。

1. 对受影响的子系统跑 `how`。
2. 用 `architect` 做并行设计探索。
3. 把吞吐检查点写成四个 todo 项。某个维度确实不适用（单文件、无扇出）时，保留该项并写 `n/a: <reason>`，而不是删掉它：
   - **先行的阻塞步骤。** 闸门在扇出之前跑。
   - **独立的工作流。** 不相交的文件、服务或层可以并行。共享写串行。
   - **共享可变状态。** 默认拆分目标（**separate-before-serializing-shared-state** 原则 skill）。只有真正的不变量才串行。
   - **最小的安全分解。** 如果一个 worker 是最优的，说明原因。
4. 用你配置的 feature 模型（默认值在 poteto-mode 的 Models 一节）把写代码委托给一个子代理，范围要具体（文件路径、命名的数据形状及其组织结构——按 **principle-model-the-domain**，散布的布尔值上建一个状态机、分支逻辑换成表/注册表、重复的形状假设换成类型化模型——都要在委托者写逻辑之前定好，以及成功判据）。按 Subagents 一节为每个子代理挑选与任务匹配的推理档位。当实现容许多种有效形状（错误处理、抽象层、测试结构）时，改用 **arena** skill 委托，让 runners 呈现备选方案、由 cross-judge 守住最终选择。强制项：没有"说明理由后跳过"的出口，Laziness Protocol 也不能覆盖它（收益是 review 分离，不是省下的行数）。被禁止派生子代理的子代理，通过直接拥有这个 diff、保持同样的 review 分离来满足此要求。不许用等待某个嵌套代理的"待命中"回复。**给每个写文件的委托者自己的工作树**（用 `isolation: "worktree"` 派生它，或递给它一个独占分支），并且不要在一个委托者仍持有的工作树里写文件或跑测试套件。在 Claude Code 上，`isolation: "worktree"` 默认从远端默认分支切出，除非 `worktree.baseRef` 设置为 `"head"`。当委托者要建立在默认分支没有的提交上时，先提交它们，用 `git worktree add <path> -b <delegate-branch> HEAD` 创建它的工作树，并在简报里点名那个基底提交。在简报的散文里给文件"设围栏"不是一把锁（**principle-separate-before-serializing-shared-state**）。注释按 **Comments**。外科手术式的编辑；上游派生的文件要对照源头重新对齐。共享原语的改进移植到全部消费方并逐个验证。放心地多提交。
5. 在匹配的表面上验证。"不确定"或表面不对不算通过。把它标出来。
6. Rebase 成小而有序的提交。后续工作堆叠起来。
   使用 **sequence-verifiable-units** 原则 skill，先构建、验证并提交每个小单元，再做下一个。
7. 如果设计存在争议，发布前跑 `interrogate`。
8. 运行 **Opening a PR**。

代码耦合的工作（一个 feature、一次 migration）交给一个 owner，检查点内联。那个 owner 在阻塞阶段之后于内部扇出。父级层的扇出用于产出互相独立工件的切片（审计、跨子系统调查、竞争性实验）。在阶段边界重写检查点。派一个新的 owner，而不是串联中断。

**回复：** 你构建了什么、你选了什么以及为什么、吞吐检查点、仍开放的决策。设计备选方案用表格。
