### Autonomous run

**退出条件由你负责。先定义「完成」，然后一路推进到位、中途不停。**

1. 在第一轮迭代之前，把退出条件表述成一条可检查的谓词（测试全绿、repro 已修好、N 个 PR 全部合并、像素 diff 为零）。
2. 按 Claude Code 的 `loop` 技能（内置技能，不是 pstack 的）选择唤醒机制。有事件可盯（CI、一次合并、一个 ref 前进）就起一个 watcher 子代理，事件发生时唤醒你，并配一个时间间隔很长的心跳兜底。没有事件就按「结果值得复查的时间点」设定固定间隔心跳。按 poteto-mode 的 Subagents 一节为每个子代理选合适的推理档位。
3. 每轮迭代只做证据能支撑的最小改动，对着谓词验证，有进展就提交，没帮上忙的改动直接丢弃。「也许有用」的双保险要回滚，不能放任它留在代码里。
   用 **sequence-verifiable-units** 原则技能编排工作顺序，每个单元验证通过再进下一个，而不是把所有检查攒到最后。
4. 中途发现的、服务于目标的问题也是你的事。坏掉的 skill、相关 bug、flaky 的验证器、评审噪音、工具故障、没人接手的遗留事项、可以修的漂移——都由你自己按 poteto-mode 处理。计划外的修复放进独立的 PR。不要把可逆的工作推给人类，也不要用 `AskUserQuestion`。只有不可逆操作、真正靠实验无法裁决的产品或偏好取舍、或真正的死路才上报。让谓词始终是主驱动，每次插完侧线修复都回到谓词上。
5. 每轮迭代用 **show-me-your-work** 技能打检查点：一行记录改了什么、谓词动了没有。
6. 谓词达成就停。平台期不是停止理由——继续推进，换打法突破它。真正的死路要上报而不是空转，但绝不为宣布胜利而放宽谓词。

**汇报：** 退出条件、跑了几轮迭代、哪些落了地、哪些被丢弃、谓词的最终状态。
