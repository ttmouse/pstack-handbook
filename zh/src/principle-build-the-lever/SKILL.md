# Build the Lever

当工作不是琐事时，构建能完成它的工具，而不是手工去做。

codemod、生成器或脚本每次都以同样的方式完成工作，并且重跑免费。工具是审查者可以阅读并重跑以检查工作的一项产物。手工做的修改只能靠重做来重新验证。一个确定性脚本把「信我」变成「跑这个」。

默认构建杠杆（lever）。只有任务琐事到一眼就能看清的几处明显修改时才跳过。

- 先手工做第一个单元来学出配方，然后构建工具。在同一个单元上重跑工具，并与手工版本做 diff 来证明它正确。让杠杆可以安全重跑。
- 对比较类工具，给它声称要比较的每种输出各塞一个已知的坏改动，确认工具能报告每一处不一致。例如，改一个总数；再单独交换条目的归属但保持总数不变。如果必需输入缺失，工具必须拒绝或把结果报告为不确定，绝不能报告为一致。把这些对照实验与实验本身放在一起，在信任它的结果之前先重跑。
- 编辑用 codemod 或脚本，重复文件用生成器，分析用 dump-to-sqlite 查询，验证用可重跑的检查。
- 确定性杠杆优于扇出。如果工具能一次处理所有单元，自己跑它。不要扇出子代理去手工完成一个脚本能做的事。
- 把工作扇出给子代理时，把杠杆写成他们都读的技能：配方、验证契约、不许触碰的围栏，放在同一份产物里。把它放在子代理的写权限之外，让他们无法悄悄改掉契约。
- 应用本原则会产出一个文件。如果你引用了它，而 diff 里没有 codemod、脚本、生成器或子代理技能，那你没有应用它。
- 当工作的寿命超过本次会话时，提交这个杠杆。

门槛是琐事与否，不是是否重复。只要杠杆正是让工作可被检查的东西，一次性的工作也值得配杠杆。按 [Laziness Protocol](../principle-laziness-protocol/SKILL.md)，构建能完成或证明这份工作的最小脚本，绝不构建框架。

本原则不同于 [Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md)，后者把反复出现的指令变成持久的护栏。本原则关注的是眼前工作的吞吐量和可审查性。要把验证本身脚本化，见 [Prove It Works](../principle-prove-it-works/SKILL.md)。
