# 维护一个形式化验证技能

在 Codex 上，遵循本技能之前先读[平台映射](../poteto-mode/references/codex-tools.md)，包括其按技能的说明。

在 GitHub Copilot 上，遵循本技能之前先读[平台映射](../poteto-mode/references/copilot-tools.md)，包括其按技能的说明。

在 Muse 上，遵循本技能之前先读[平台映射](../poteto-mode/references/muse-tools.md)，包括其按技能的说明。

在 Antigravity 上，遵循本技能之前先读[平台映射](../poteto-mode/references/agy-tools.md)，包括其按技能的说明。

形式化检查证明它所描述之物的一个属性。当代码变了而验证没变，检查可以继续通过，同时描述的是不再存在的代码。那种通过是危险的情形，因为它看起来像一个证明。本技能是 `/create-formal-verification-skill` 生成的形式化验证技能的维护循环，也适用于任何对具名代码运行模型检查器、证明器或代码级验证器的项目本地技能。项目本地技能处理代理在使用该技能时发生的变更。本技能处理那些绕过它的变更：合并、不经过该技能做出的编辑，以及跨许多提交累积的漂移。

## 结果

给每个检查一个结果，并说明是哪个：

- **in sync**：自上次同步以来没有任何变更改变检查所描述的内容，且检查通过。
- **updated**：代码变了，验证现在描述新代码，且检查通过。
- **bug**：验证描述的是当前代码，而代码违反属性。这是关于代码的发现，不是漂移。
- **blocked**：检查无法重新对齐或无法运行。准确说明原因。

一个检查可以既是 updated 又是 bug：更新让验证重新描述代码，然后属性在其上失败。

## 编辑范围

只编辑验证：模型、harness、属性文件，以及形式化验证技能本身。运行期间绝不编辑产品代码，除非用户要求。当属性在当前代码上失败时，不要为让它通过而削弱属性或模型。报告该失败。

## 流程

1. **找到检查。**形式化验证技能没有固定名字，所以按它做的事找：一个对具名代码运行模型检查器、证明器或其他验证器的项目技能。`/create-verification-skill` 写出的项目 `verify` 技能驱动应用，不算。读找到的每一个，或用户点名的那个。对每个检查，收集它的属性、覆盖的代码、边界与假设、运行命令，以及最后一次确认它描述代码的提交。如果不存在形式化验证技能，停下并指向 `/create-formal-verification-skill`。如果技能没有记录同步提交，用最后一个改过验证文件的提交，并说明你这么做了。

2. **原样跑一遍。**改任何东西之前把每个检查跑一次，记录结果。这里的通过不说明代码正确。它说明旧描述仍然成立。这里的失败可能是漂移也可能是 bug。在第 5 步之前不要下判断。

3. **读被覆盖代码的每一处变更。**把覆盖文件从同步提交 diff 到当前提交，并读每条提交信息。同时找移动的代码：被重命名、拆分或移到别的文件的被覆盖函数，仍然是被覆盖代码。同时找触及检查所守护状态的新代码，比如写相同字段的新函数。对每处变更，判断它是以下哪一种：
   - **无影响。**变更不改变验证描述的任何东西，比如格式化、注释或验证未覆盖的代码路径。对照模型或 harness 判断，不要对照提交信息。
   - **验证不再描述代码。**原来一个不可分动作的步骤现在是两个，分支增删，检查移位，新路径到达被守护状态，或某个值的范围变了。模型或 harness 必须改。
   - **承诺被有意改变。**变更改变了代码的承诺，且变更中的证据表明这是有意的：doc comment、测试、changelog 或提交信息。属性必须改，且你必须引用该证据。
   - **承诺可能被破坏。**代码变了，没有任何证据说承诺变了。把随之而来的失败当作 bug 候选。

4. **从代码更新，而不是从结果更新。**修改模型或 harness，让每个被变更的部分重新指向评审者能打开的代码，并保持代码中一个不可分的步骤在验证中仍是一步。重跑之前就依据代码写好更新，不要被什么能让检查通过来塑形。只对被有意改变的承诺修改属性。写下旧措辞、新措辞和证据。保持边界，除非变更让它们失真。如果必须缩小边界，在报告中说明。

5. **重跑并评判每个结果。**
   - **通过：**检查可能是在一个已丧失失败能力的描述上通过的。按属性所防范的方式破坏新代码，比如删掉一个新检查或重排一个新步骤，确认检查能抓住它。然后撤掉这个破坏。
   - **失败：**把反例对着真实代码逐步重放。如果某一步在代码中不可能发生，验证是错的。修验证，并说明错在哪。如果每一步都可能发生，这就是 bug。指出引入它的提交，用代码自己的语言把反例讲成步骤序列，并用一句话说明危害。如果对真实代码的廉价测试或复现能展示该 bug，把它作为证据加进报告。不要把它提交进产品代码。

6. **更新形式化验证技能。**更新每个检查覆盖的代码、命令、边界、假设和同步提交。把同步提交设为你检查的那个提交。被阻塞的检查不要移动同步提交，并在报告中说明。然后以下一个代理的身份把形式化验证技能完整走一遍，确认它的步骤仍然可运行。

## 报告

对每个检查告诉用户：

- 结果，以及你读过的提交；
- 验证里改了什么、为什么，每处变更一个简短理由：代码变了形态，或承诺被有意改变（附证据）；
- 重跑结果，以及你用来证明更新后的检查仍会失败的破坏；
- 每个 bug，用平实的话：以代码语言表述为步骤的反例、危害，以及引入它的提交；
- 验证仍然不覆盖什么，包括它应当覆盖却不覆盖的新代码。

直说哪些失败是验证的漂移、哪些是代码的 bug。对一个更新前通过、更新后失败的检查，说明旧通过建立在过期的描述上。

把验证更新放进一个独立的变更里，与任何产品修复分开。
