# Maintain a formal verification skill

在 Codex 上，先阅读[平台映射](../poteto-mode/references/codex-tools.md)（包括其中的各技能说明），再执行本技能。

在 GitHub Copilot 上，先阅读[平台映射](../poteto-mode/references/copilot-tools.md)（包括其中的各技能说明），再执行本技能。

在 Muse 上，先阅读[平台映射](../poteto-mode/references/muse-tools.md)（包括其中的各技能说明），再执行本技能。

在 Antigravity 上，先阅读[平台映射](../poteto-mode/references/agy-tools.md)（包括其中的各技能说明），再执行本技能。

形式化检查证明的是它所描述对象的一条性质。当代码变了而验证没跟上时，检查可能继续通过，但描述的已经是不再存在的代码。这种通过最危险，因为它看起来像一份证明。本技能是 `/create-formal-verification-skill` 生成的形式化验证技能的维护循环，也适用于任何对着指定代码运行模型检查器、证明器或代码级 verifier 的项目本地技能。项目本地技能处理的是 agent 在使用它时顺带做出的改动；本技能处理的是绕过它的那些改动：合并、没走技能的直接编辑，以及跨许多提交累积起来的漂移。

## 结果

每个检查给出一个结果，并说明是哪个：

- **in sync**：上次同步之后没有任何改动影响检查所描述的内容，且检查通过。
- **updated**：代码变了，验证现在描述的是新代码，且检查通过。
- **bug**：验证描述的是当前代码，但代码违反了性质。这是关于代码的发现，不是漂移。
- **blocked**：检查无法重新对齐或无法运行。准确说明原因。

一个检查可以同时是 updated 和 bug：更新让验证重新描述了代码，然后性质在上面失败了。

## 编辑范围

只编辑验证本身：模型、harness、性质文件，以及形式化验证技能自身。运行期间绝不编辑产品代码，除非用户要求。某条性质在当前代码上失败时，不要为了让它通过而弱化性质或模型。把失败报告出来。

## 流程

1. **找到检查。** 形式化验证技能没有固定名字，按它做的事来找：对着指定代码运行模型检查器、证明器或其他 verifier 的项目技能。`/create-verification-skill` 写出的项目 `verify` 技能是驱动应用的，不算。把你找到的每个（或用户点名的那个）读一遍。对每个检查，收集：性质、覆盖的代码、边界和假设、运行命令，以及最后一次确认它描述代码的提交。如果没有任何形式化验证技能，停下来并指向 `/create-formal-verification-skill`。如果技能没有记录同步提交，就用最后一次改动验证文件的提交，并说明你这么做了。

2. **按现状跑一遍。** 在改动任何东西之前，每个检查先跑一次并记录结果。这里的通过不说明代码正确，只说明旧描述仍然成立。这里的失败可能是漂移也可能是 bug，第 5 步之前不判断是哪种。

3. **通读覆盖代码的每一次改动。** 把覆盖文件从同步提交 diff 到当前提交，并读每条提交信息。还要找搬动过的代码：被重命名、拆分或移到别的文件的被覆盖函数，仍然是覆盖代码。还要找触碰检查所守护状态的新代码，比如写同一批字段的新函数。对每处改动，判断属于哪一类：
   - **无影响。** 改动没有改变验证描述的任何东西，比如格式、注释，或验证不覆盖的代码路径。这个判断要对照模型或 harness 来做，不能只看提交信息。
   - **验证不再描述代码。** 原来一个不可分的步骤现在变成两步，分支增删，检查搬了位置，新的路径抵达被守护的状态，或某个值的范围变了。模型或 harness 必须改。
   - **承诺有意变更。** 改动改变了代码的承诺，且改动中有证据表明这是有意的：文档注释、测试、changelog 或提交信息。性质必须改，且要引用那份证据。
   - **承诺可能被违反。** 代码变了，且没有证据表明承诺变了。随之而来的失败按 bug 候选对待。

4. **依据代码更新，而不是依据结果。** 修改模型或 harness，让每个改过的部分重新指向审查者能打开的代码，并保持代码里一个不可分的步骤在验证中仍是一个步骤。重跑之前先从代码写出更新内容，不要被「怎么改才能让检查通过」带偏。只有承诺有意变更时才改性质，写下旧表述、新表述和证据。边界保持不变，除非改动使它失效。必须缩小边界时，在报告中说明。

5. **重跑并对每个结果下判断。**
   - **通过：** 检查现在可能在一个已经失去失败能力的描述上通过。按性质防范的方式破坏新代码，比如删掉一个新加的检查或调换一个新步骤的顺序，确认检查能抓住它，然后把破坏撤掉。
   - **失败：** 把反例在真实代码上逐步重放。某一步在代码里不可能发生，就是验证错了——修验证，并说明错在哪。每一步都能发生，就是 bug。指出引入它的提交，用代码自己的语言把反例讲成一步步的序列，用一句话说明危害。如果一次廉价的测试或真实代码复现能展示这个 bug，把它作为证据写进报告，但不要提交进产品代码。

6. **更新形式化验证技能。** 更新每个检查覆盖的代码、命令、边界、假设和同步提交。同步提交设为你检查过的那个提交。blocked 的检查不要移动同步提交，并在报告中说明。然后按下一个 agent 的方式把形式化验证技能完整走一遍，确认它的步骤仍然能跑。

## 报告

对每个检查告诉用户：

- 结果，以及你读过哪些提交；
- 验证改了什么、为什么改，每处改动给一个简短理由：代码变了形状，或承诺有意变更（附证据）；
- 重跑结果，以及你用来证明更新后的检查仍会失败的破坏；
- 每个 bug，用平实的语言：按代码自己的语言讲成步骤的反例、危害、引入它的提交；
- 验证仍然不覆盖的部分，包括它应当覆盖却没有覆盖的新代码。

直说哪些失败是验证漂移、哪些是代码 bug。更新前通过、更新后失败的检查，要说明旧的通过是基于一份过时的描述。

验证更新单独放进一个独立的变更里，和任何产品修复分开。
