# Benchmark checklist

只要你要产出一个性能数字——PR 的前后对比、一个性能回退的结论、一个 hillclimb 测试台，或一次库/配置选型——就用它。每个问题都用一次真实运行得到的证据回答，不是对代码的猜测。

用户只要快速量级的场景，跑一次就够了。但问题 4 和 7 仍然要查，并说明只有一次运行。其余问题在该次运行看起来正常时可以跳过。在几个选项之间做选择永远不算快速量级。

## Before you run anything

- 用你打算交付的原话写下预期结论（"60k 行数据集上 export 的 p50 快了 30%"）。后面的问题就是检验这句话。
- 读测量脚本。记下它计时什么、统计什么、忽略什么。
- 用 `uptime` 查负载，用 `nproc` 查核数。机器忙的话，搞清楚在跑什么。停不掉的话，把两侧交错执行让它们吃同样的噪音，并在报告里说明。

## The questions

1. **为什么不翻倍？** 说出限制因素。profile 放在你不上报的那次运行里做，因为 profiler 和 tracer 会拖慢工作本身。用每进程 CPU（`top`、`pidstat`）、运行时 profiler（`node --cpu-prof`、`py-spy`、`perf`）、I/O 等待、系统调用计数（Linux 上 `strace -c`），然后把热点映射回源码。负载生成器也要盯：如果它先饱和，你测的是负载生成器。某个改动没让数字动，限制因素就能解释原因——所以先找到它，再下"改动没用"的结论。
2. **调优了吗？** 每一侧都按生产环境的方式跑：release 构建、生产 flag 和环境变量、批处理和事务设置、连接池、缓存冷热与生产一致、相同的版本和数据。有一侧跑在默认配置上，你比的就是配置，不是实现。限制因素是一项设置（每行一次 commit、debug 构建、缺索引）就意味着那一侧没调优。先调优再测，然后才选赢家。调不动就别从这次运行里选赢家。用户在选型时，把结论收窄到"今天交付的代码"也救不了这一点，因为他们采纳的是那个选项，不是今天的设置。
3. **破上限了吗？** 做算术。每秒字节数对磁盘和网络带宽，每秒操作数乘单次成本对你的核数，省下的时间对被改部分原本的耗时。去掉占整体运行 10% 的部分，最多只能快约 11%。超出上限的结果测到的是别的东西——缓存、空操作，或者一个 bug。
4. **报错了吗？** 统计失败数和非成功响应，并确认输出正确，而不只是存在。被拒绝的请求通常很快，超时和重试很慢。脚本不数错误就加上这个计数。
5. **能复现吗？** 每侧至少跑 5 次，交替进行（A, B, A, B……），让预热、惰性初始化、缓存和漂移不偏袒任何一侧。报告中位数和区间。差距小于运行间波动就是无可测差异。结论接近临界时，用秩和检验或测试台自带的统计。
6. **重要吗？** 在任何微观结果旁边，用贴近真实的数据规模和并发测一遍用户实际等待的端到端路径，并把微观结果报告为整体的一个占比。一个占请求 1% 的辅助函数，再快也只能让请求快 1%。
7. **这个活儿真的发生了吗？** 确认工作发生在被计时的区间内：请求到达了服务器、行真的写进去了、字节真的读了、代码真的用了结果。惰性代码（没人迭代的生成器、没人 await 的 promise、JIT 可以丢弃的结果）和超时都会给从未发生的工作生成数字。

## Report

- 结论先行：更快、更慢、无可测差异，或无法定论。
- 数字带单位、运行次数、区间和限制因素。例如："p50 41 ms → 33 ms，每侧 7 次运行取中位，之后区间 32-35 ms，瓶颈是单核 JSON 解析。"
- 出现以下情况时结论标"无法定论"：你声称有差异但说不出限制因素、某一侧没调优、或问题 4 和 7 没查。写清缺什么。
- PR 正文只保留一个主数字。运行次数、区间和限制因素证据放进链接的产物或笔记文件。

## Other perf material

- **Perf issue** playbook 用基线做规划之前，先审这条基线；之后的每个数字同样要审。
- **Hillclimb** playbook 的测试台冻结之前先审。冻结后它会打印错误计数和工作量计数，每次 keep-or-revert 判定就免费核掉了问题 4 和 7。
