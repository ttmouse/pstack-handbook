这本是「给 PR 化妆，不动手术」：提交历史、描述、审查备注都收拾干净，但代码行为一个字节都不变。

拆解里面的黑话：

- **历史清理**：把嘈杂的 commit 重排分组（schema → 核心逻辑 → 接线 → UI → 测试），需要 force-push，所以必须先经你同意。
- **树校验**：重写历史前先记下原 diff 的树哈希，重写后再比对——哈希不一致说明内容被弄丢了，绝不推送。
- **审查者指引**：在 PR 描述里写 TL;DR、区分核心文件与生成文件、点名风险，让审查者五分钟看懂。

什么时候用它：PR 已经写完但很难审（提交乱、描述过时、清理和逻辑混在一起）。什么时候别用：想改代码本身——那是另一个任务；PR 大到靠描述救不了时，它也只会建议拆分而不是抛光。
