pstack · 技能分册

需要人来输入的技能

pstack 的技能分两类：路由器按任务自动带出的，和必须由你发起的。这一页只讲后者：什么时刻该你输入、输入什么、能得到什么。所有技能都由你发起——你输入命令，或明确让 Agent 调用；执行阅读、修改和检查的是 Agent。

按本手册与本机 pstack 技能说明整理 · 2026 年 11 月 · 案例可直接复制

运行时前缀：Claude Code 用 /pstack:how，Codex 用 $pstack:how，其余 runtime 按各自写法。技能源文件在本机 ~/.agents/skills/<名字>/SKILL.md，想改行为就改那份文件。

哪些要你来输入

判断标准：路由器猜不到、必须由你的判断触发的技能，才需要你输入。三类东西永远不用你手敲：playbook 只能被路由器读；24 条原则由它按场景自选；修 CI、去 slop 这类执行型技能，多数会随 playbook 自动带出。

需要你输入的集中在六个位置：派任务的开场、对齐目标、理解项目、纠错固化、验证基建、并行与评审。下面按这个顺序列，最后补一组日常状态技能。

入口：启动一次任务

poteto-mode

何时：派一项新任务时，作为开场输入一次。

/pstack:poteto-mode 修好点一次保存却存出两条记录的问题。完成标准：真实页面点 5 次保存恰好 5 条，给前后截图。

得到：它判断任务类型，挑一本 playbook，把步骤抄进待办清单，再按步骤调用技能和子代理。你描述任务，不要自己列步骤。

第 1 步 · 对齐目标

sharpen

何时：自己说不清要什么、写出的指令含糊时，派活前先跑。

/pstack:sharpen 我想让保存别再重复

得到：一条边界和完成标准都清楚的指令。它帮把任务变深而不是变大，改写的是你的原话。

in-your-own-words

何时：需求复杂、怕理解偏，动手前确认一次。

/pstack:in-your-own-words

得到：Agent 用自己的话复述你的目标和完成标准，暴露误解；有信息缺口时它会反过来问你。

第 2 步 · 理解项目

how

何时：改代码前想懂某段怎么工作、该放在哪一层。

/pstack:how 保存按钮到写入数据库的链路是怎么走的？关键函数在哪？

得到：带文件路径和关键函数的走读说明。也可以对 Agent 说“用 /how 读懂这段再改”。

why

何时：想知道为什么这样设计、当时的权衡是什么。

/pstack:why 保存请求为什么走重试队列？

得到：设计理由、备选方案和依据，引用提交与讨论，不猜。

recall

何时：跨会话接续：找回之前的结论、已修问题和未完事项。

/pstack:recall 上周讨论保存逻辑时我们定了什么结论？

得到：一份当前状态简报：相关决策、修复记录、悬而未决的事，注明来源。

第 3 步 · 纠错固化

correct

何时：同类错误反复出现之后；目标是让错误无法复发，而不是再提醒一遍。

/pstack:correct

得到：找出重复出现的错误和根因，每个错误配一条架构调整、lint 或测试，并验证检查真能拦住它。

第 4 步 · 验证基建

create-verification-skill

何时：项目还没有能自动驱动 App 的验收方式时，建一次。

/pstack:create-verification-skill

得到：一份验证技能加功能地图：Agent 能启动产品、按用户路径操作、给出截图等证据。

maintain-verification-skill

何时：功能地图过时、验证开始漏掉新功能时。

/pstack:maintain-verification-skill

得到：验证技能与功能地图回到和当前代码一致，不再按旧地图验收。

create-formal-verification-skill

何时：并发、重试、状态机、解析器这些测试够不到的地方。

/pstack:create-formal-verification-skill 检查保存重试队列不会重复投递

得到：一个能重复运行的模型检查；违反规则时给出最短违规路径。

maintain-formal-verification-skill

何时：改动碰到了已验证代码，模型开始和代码失真时。

/pstack:maintain-formal-verification-skill

得到：模型、检查与代码重新一致，并说明哪些失败是代码变了、哪些是模型旧了。

statechart

何时：想核对一个状态机或产品流程是否闭环。

/pstack:statechart 订单状态机

得到：一张 Mermaid 状态图，加每条违反规则的状态路径。

第 5 步 · 并行与评审

swarm

何时：任务可拆分、结果可批量验证：覆盖矩阵、赛跑、并行探索。

/pstack:swarm 覆盖矩阵：10 个页面 × 3 种视口各验证一遍

得到：一份汇总报告，每一路的结果都带证据；失败路径会被收拢成清单。

architect

何时：改动跨模块边界、要先定形状再动手。

/pstack:architect 给保存链路画类型草图再动手

得到：类型、签名和模块草图；确认草图后，实现按它填。路由器在跨边界时也会自己调它。

interrogate

何时：重要改动合并前，想被刻意挑刺一轮。

/pstack:interrogate 审这份 diff，试图推翻它

得到：只有被真实运行证实的发现会留下来，猜测不算数。

babysit

何时：PR 已经开出，需要有人盯 CI 和评审意见到可合并。

/pstack:babysit

得到：失败的 CI 修好、简单的评审意见处理完，PR 达到可合并状态；合并权仍在人。

日常状态与复盘

ketchup

何时：离开一阵回来，要接上这段对话的进度。

/pstack:ketchup

得到：大白话列出发生了什么；每件等你决定的事都附上决策所需的选项。

what-did-i-get-done

何时：要汇总一段时间内落地的成果。

/pstack:what-did-i-get-done 最近两周

得到：按主题归类的交付清单，来自真实提交记录。

show-me-your-work

何时：长任务需要可复查的决策记录时开启。

/pstack:show-me-your-work

得到：一行一条的决策日志：做了什么、为什么、证据、结果。

figure-it-out

何时：改动又大又模糊，现成 playbook 套不上。

/pstack:figure-it-out 把导出模块迁到新格式

得到：一份可审计的执行方案：假设、阶段、每步验收判据。

setup-pstack

何时：装完 pstack 或换模型后，配置各角色用哪个模型。

/pstack:setup-pstack

得到：按本机可用模型生成的角色配置表。
